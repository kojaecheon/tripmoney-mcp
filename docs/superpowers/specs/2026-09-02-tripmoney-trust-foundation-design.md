# TripMoney 00 신뢰 기반 하위 설계

- 작성일: 2026-09-02
- 상태: 대화형 설계 4개 섹션 승인 완료, 이 작성본에 대한 사용자 최종 승인 대기
- 상위 명세: [사업화 설계](2026-08-26-tripmoney-commercialization-design.md)
- 기준 코드: `0ac5366`의 구현 파일(문서 외 변경 없음)
- 실행 체계: Codex 구현·검증, Claude 비식별 독립 검토, 창업자 운영 승인
- 승인 경계: 작성본 승인 → `writing-plans` 구현 계획 → 별도 실행 승인. 이 문서는 코드·배포·DB 초기화의 실행 승인이 아니다.

## 1. 목적과 완료 결과

00은 서비스를 추가하는 단계가 아니라 실제 고객 데이터를 다룰 수 있는 신뢰 기반을 만드는 단계다. 레거시 데모를 운영 환경에서 닫고, 직원 신원과 DB 권한을 분리하며, 개인정보 삭제와 복구가 실제로 작동한다는 증거를 만든다.

완료 결과는 세 슬라이스다.

| 슬라이스 | 결과 | 의존성 | 완료 후 실제 고객 접수 |
|---|---|---|---|
| 00A | demo-only 경계, 중앙 설정, 최소권한 기반, CI, 직접 식별정보를 남기지 않는 로그 | 없음 | 금지 |
| 00B | 직원 인증, Admin/Reviewer, 최소 베타 신청·동의·보유·삭제 기능 | 00A | 금지 |
| 00C | 외부 삭제 저널, 백업·복구 훈련, 통합 출시 증거 | 00A·00B | 외부 개인정보 검토와 창업자 수동 승인 후 베타 연락처 접수만 검토 가능 |

`REAL_DATA_INTAKE_ENABLED=false`는 00A~C, 외부 개인정보 게이트, 최종 운영 승인이 모두 끝날 때까지 유지한다. 이 플래그가 켜져도 미구현 주문·결제·영수증·정산·공유 경로는 열리지 않는다. 각 후속 하위 명세의 승인과 개별 플래그가 별도로 필요하다.

### 1.1 승인된 결정

- 기존 Supabase 프로젝트는 유지한다. 현재 데이터는 모두 폐기 가능한 데모이며 실제 동의 데이터로 승격하지 않는다.
- Production에서는 `/mcp`, `/prototype`, `/api/web`를 항상 404로 닫는다. 합성 데모는 Local·Preview에서만 제공한다.
- 직원은 창업자 Admin 1명과 보조 운영자 Reviewer 1명으로 시작한다.
- Reviewer는 승인된 마스킹 조회와 내부 QA 의견 작성만 가능하다. 고객 데이터 변경·삭제·설정·정산 릴리스 승인은 불가하다.
- 접근 A: Supabase Auth를 서버에서 검증하고 기존 `pg` 기반 코드를 역할별 제한 연결·view·함수로 분리한다.
- PostgREST/RLS 중심 전면 재작성, 별도 인증 백엔드 도입은 하지 않는다.

### 1.2 비목표

00에서는 결제·환불·주문·콘시어지 케이스, OCR·업로드, 금액 모델 전환, 정산 잠금, 고객 grant·공유, 계좌 수집, 조직·구독을 구현하지 않는다. 기존 11개 MCP 도구 전체의 재작성, 프레임워크 전환과 운영 대시보드 고도화도 하지 않는다.

## 3. 환경과 공개 표면

### 3.1 중앙 설정 계약

환경변수 해석은 하나의 typed 설정 모듈에서만 수행한다. 기능 코드는 `process.env`를 직접 읽지 않고 검증된 설정을 받는다.

- 환경은 `local`, `preview`, `production`, `test` 중 하나다. 배포 플랫폼의 환경값과 앱 환경값이 충돌하거나 불명확하면 실제 데이터 관련 표면을 열지 않는다.
- boolean 플래그는 정확한 문자열 `true`만 활성으로 인정한다. 누락·오타·알 수 없는 값은 활성화하지 않으며 구성 오류를 내부 진단에 남긴다.
- 필수 구성 누락 시 관련 API는 503을 반환한다. Production의 금지 데모 경로는 구성과 무관하게 404다.
- 프로덕션 DB·Auth 프로젝트 식별자와 승인된 배포 호스트를 묶어 검증한다. Preview·Local에는 프로덕션 자격정보를 주입하지 않는다.
- DB 연결 후 읽기 전용 배포 식별자를 확인해 예상 환경·프로젝트·DB 역할과 일치하지 않으면 요청을 처리하지 않는다.
- 실제 데이터 연결을 데모 모듈에 전달하지 않는다. 데모 모드에서 실제 데이터 연결을 요청하면 초기화가 실패한다.
- 모든 플래그를 끄는 것은 신규 접수 중단이다. 기존 데이터의 권리행사·삭제·안전 진단까지 끄지 않는다.

### 3.2 경로 계약

| 표면 | Production | Local·Preview |
|---|---|---|
| `/`, `/index.html` | 공개 랜딩, 접수 비활성 상태를 명확히 표시 | 합성 시연 가능 |
| `/mcp`, `/api/mcp` | 모든 메서드 404 | 명시적 데모 플래그+키, synthetic-only |
| `/prototype`, `/app.html` | 모든 메서드 404 | 명시적 데모 플래그, synthetic-only |
| `/api/web` 및 동일 핸들러의 별칭 | 모든 메서드 404 | query 키 금지, 데모 키 필수, synthetic-only |
| `/api/beta` | 00 완료·외부 승인·두 접수 플래그 충족 전 503 | 별도 DB의 합성 신청만 |
| `/operator`, `/api/operator/*` | 00B 이전 미제공, 이후 직원 인증 필수 | 테스트 Auth·합성 DB만 |
| 인증 시작·callback | 00B 설정 검증 후 최소 로그인 기능만 공개 | 환경별 정확한 callback URL |
| `/health`, `/api/health` | 민감정보 없는 `ok`/`unavailable`·요청 ID만 | 같은 공개 계약 |
| 후속 checkout/intake/review/share | 미구현·비활성 | 00에서 구현하지 않음 |

정적 파일·API 원래 경로·rewrite·trailing slash·대소문자/인코딩 변형·GET/POST/HEAD/OPTIONS도 우회 테스트한다. Production 산출물에 데모 HTML을 포함하지 않거나 동일한 서버 경계를 통과시킨다. 단순히 `/prototype` rewrite만 제거하는 방식은 수용하지 않는다. Vercel·로컬 서버·Docker/Kakao 서버에도 같은 환경 정책을 적용한다.

Local 서버는 loopback에 바인딩한다. 외부 바인딩을 허용하는 개발 설정이 있어도 키 검사와 synthetic-only 경계는 제거하지 않는다. 계좌 입력·출력, Toss 딥링크, 계좌가 포함된 CSV·공유는 00A에서 모든 환경에 걸쳐 비활성화한다.

### 3.3 플래그

상위 명세의 `REAL_DATA_INTAKE_ENABLED`, `BETA_LEAD_INTAKE_ENABLED`, `MCP_DEMO_ENABLED`, `DEMO_SURFACES_ENABLED`, `PAYMENTS_ENABLED`, `RECEIPT_UPLOAD_ENABLED`, `PAYOUT_METHODS_ENABLED`, `SETTLEMENT_FINALIZATION_ENABLED`, `ORGANIZATIONS_ENABLED`를 중앙 계약으로 유지한다.

- Production에서 데모 플래그를 `true`로 입력해도 데모 경로는 열리지 않는다.
- 베타 접수는 두 접수 플래그, 정책 버전, Auth·DB·삭제·백업 준비상태와 승인된 출시 증거가 모두 필요하다.
- 후속 기능 플래그는 00에서 활성화할 수 없다. 특히 계좌·조직은 별도 후속 설계 승인이 필요하다.
- 웹 설정 화면은 만들지 않는다. 초기 플래그 변경은 창업자의 배포 구성 변경과 변경 기록으로 관리한다.

## 4. 데이터·DB 최소권한 계약

### 4.1 분류와 레거시 자격정보

- `trips.data_class`, `beta_leads.data_class`는 `quarantined|demo|real`의 NOT NULL 값이며 default가 없다.
- 기존 행은 마이그레이션에서 `quarantined`로 표시하고 제품 경로에서 거부한다. 승인된 초기화 런북으로 전량 삭제하며 Production으로 재분류하지 않는다.
- 신규 생성은 호출 경로가 분류를 명시한다. 요청 본문의 `data_class`를 신뢰하지 않는다. 분류는 런타임에서 변경할 수 없다.
- Production 런타임은 `real`만, 데모 런타임은 `demo`만 접근한다. `quarantined`는 어느 제품 역할도 접근하지 못한다.
- `real` 여행의 `api_key`, `share_token`은 반드시 NULL이다. 0008에서 레거시 무조건 default·NOT NULL을 조건부 제약으로 전환하며, demo 생성만 키를 명시적으로 만든다.
- `members.account_no`는 부모 여행 분류까지 검증하는 DB 제약/트리거로 real에서 NULL을 강제한다. 00의 모든 생성·변경 함수는 환경과 무관하게 계좌 입력을 거부한다.
- 자식 테이블의 접근은 부모 trip 분류를 따라간다. `expense_shares`처럼 직접 trip_id가 없는 관계도 expense와 member의 여행 일치를 DB에서 강제한다.
- schedules/expenses의 멤버·일정 참조, expense_shares의 expense/member 참조에 대해 cross-trip 삽입·갱신을 거부한다. 부모·자식 분류나 FK를 바꾸어 경계를 우회할 수 없어야 한다.

### 4.2 역할과 자격정보

직원 역할과 시스템 작업 역할은 다르다. 세 주요 역할 외에 인증 전 조회·공개 접수·자동 삭제를 위한 좁은 시스템 역할을 둔다. 이는 신규 제품 기능이 아니라 A 접근의 최소권한 구현 계약이다.

| DB 역할 | 허용 기능 | 금지 |
|---|---|---|
| `tm_admin_app` | 마스킹 운영 조회, 사유 있는 연락처 열람 함수, 삭제 요청, 기존 직원 활성 상태 관리 | 원본 테이블 직접 조회, 감사로그 수정·삭제, DDL |
| `tm_reviewer_app` | 승인된 마스킹 view 조회, 내부 QA 의견 추가 | 원본 연락처, 고객 데이터 변경·삭제, 설정, 실제 정산 릴리스 승인 |
| `tm_auth_app` | 검증된 Auth UUID·session_id의 활성·역할·세션 시각 조회, 해당 세션 폐기 기록 추가 | 리드·여행 조회, staff 권한 변경, Auth 원본 테이블 직접 접근 |
| `tm_lead_app` | 고정된 베타 신청 저장 함수 실행·접수증 반환 | 목록·원본 조회, 임의 UPDATE/DELETE |
| `tm_privacy_job` | 만료/삭제 대상의 불변 ID와 기한 조회, 저널 확인된 삭제·기한 경과 보안기록 정리 | 원본 연락처 조회, staff·고객 데이터의 임의 UPDATE, 제한 함수 밖 DELETE |
| `tm_demo_app` | 비운영 DB의 demo 전용 view·함수 | real/quarantined, 운영 DB 연결 |
| `tm_migration` | 승인된 마이그레이션·초기화·복구 | 서버리스·API 런타임 주입 |

- 역할마다 별도 DSN·pool을 사용하고 단일 광역 `DATABASE_URL` fallback을 없앤다. client 입력으로 pool을 고르거나 연결을 `SET ROLE`로 승격하지 않는다.
- 런타임 역할은 소유자·superuser·BYPASSRLS·다른 역할의 member가 아니다. 원본 테이블·스키마 CREATE·함수의 기본 PUBLIC EXECUTE를 회수한다.
- 조회는 열을 명시한 `security_barrier` view, 변경은 좁은 검증 함수 또는 자동 갱신 가능한 view의 `WITH CASCADED CHECK OPTION`을 사용한다.
- join view에 CHECK OPTION만 붙여 쓰기가 보호된다고 가정하지 않는다. 다중 테이블 변경은 제한 함수와 제약으로 처리한다.
- 보안 정의자 함수의 소유자는 NOLOGIN으로 두고, 고정 search_path·스키마 한정 참조·명시 입력 검증·최소 EXECUTE 권한을 적용한다.
- Auth/DB 공급자의 서비스 키와 migration 비밀번호는 브라우저에 전달하지 않는다. 세션 사용자 정보를 가진 Auth client는 요청별로 생성한다.
- 역할 DSN 분리는 DB capability를 강제하지만 동일 서버가 완전히 침해된 경우까지 직원 간 물리적 격리를 보장하지는 않는다. 검증된 직원 ID를 SQL에 전달하는 책임은 서버에 있으며, DB 역할과 JWT 사용자 역할을 혼동하지 않는다.

00은 미래 고객·거래 CRUD를 미리 열지 않는다. Admin의 향후 업무 변경 권한은 해당 후속 명세와 마이그레이션에서 필요한 함수만 추가한다.

### 4.3 마이그레이션과 안전 전환

`0001~0007`은 변경하지 않는다. 00A는 `0008_internal_staff_auth_real_data_boundary.sql`, 00B는 `0009_privacy_consent_retention.sql`을 추가한다. 0008에는 `internal_staff`, `staff_session_revocations`와 좁은 인증 조회·폐기 함수가 포함된다. 0009에는 00C에서 사용할 삭제 요청·tombstone 상태도 포함한다. 적용된 파일을 00C에서 다시 고치지 않는다. 추가 변경이 필요하면 후속 번호를 충돌 없이 배정하고 상위 순서표를 함께 갱신한다.

전환 순서는 운영 데모 차단 배포·검증 → 정확한 프로젝트/행 수 확인·암호화 덤프 → 기존 행 격리 → 승인된 데모 전량 정리 → 새 역할·제약 검증 → 역할별 자격정보 전환·기존 광역 앱 자격정보 회수 → 역할 기반 앱 검증이다. 실제 정리·배포 시점에는 대상 프로젝트와 복구 가능성을 다시 확인한다.

운영 프로젝트 자체, Auth 설정, 마이그레이션 이력은 삭제하지 않는다. 실제 데이터가 없다는 사용자 확인에 근거한 일회성 데모 정리만 일반적인 dual-write·두 릴리스 관찰의 예외다. 이후 실데이터 스키마 변경은 상위 expand/contract 규칙을 따른다. 스키마를 파괴적으로 되돌리는 rollback 대신 앱 롤백·플래그 차단·후속 정합성 마이그레이션을 쓴다.

## 5. 직원 인증과 세션

### 5.1 초기 등록과 로그인

Supabase Auth에 창업자와 Reviewer를 수동 초대/등록하고, 각 Auth UUID를 `internal_staff`에 연결한다. 공개 signup은 비활성화하며 로그인 요청의 `shouldCreateUser`도 false다. 실제 직원 이메일은 비밀 구성/공급자 관리 화면에서만 다루고 저장소·AI 검토에 적지 않는다.

매직링크는 서버 callback에서 세션으로 교환한다. 브라우저가 직접 Supabase 데이터 API를 사용하는 구조가 아니라 서버가 인증·데이터 접근을 담당하는 구조다. 허용 Site URL·callback은 환경별 정확한 URL로 제한하며 Production에 Preview wildcard를 넣지 않는다.

로그인 시작 시 서버가 일회성 state를 발급해 브라우저의 짧은 수명 HttpOnly 쿠키와 결합한다. callback은 허용된 이메일 token_hash 교환, state 일치·만료 검증 후 세션을 발급하고 query를 제거한 고정 운영자 경로로 redirect한다. 임의 `next` URL은 허용하지 않는다. 다른 브라우저에서 열었거나 state가 없으면 재시작을 안내한다. 인증 URL·query는 접근로그에서 제거하며 callback에는 외부 스크립트·추적기를 넣지 않는다.

서버는 다음을 순서대로 확인한다.

1. 허용 알고리즘의 JWT 서명과 고정 Supabase 프로젝트의 JWKS
2. issuer, audience, 만료, 유효한 `sub`와 `session_id`
3. Supabase 서버 사용자 검증과 실제 세션 활성 레코드·앱 폐기 기록 조회
4. 해당 UUID의 `internal_staff.active`, 역할, 세션 차단 기준
5. 요청 작업의 역할 권한 및 DB pool

JWKS 검증을 위해 해당 프로젝트의 비대칭 signing key 설정을 운영 전제조건으로 확인한다. 서명 없는 decode, 임의 issuer/JWKS, legacy 공유 비밀키 fallback을 허용하지 않는다. 캐시 만료·키 회전은 공식 문서에 맞추고, 키가 없거나 Auth/DB 검증에 실패하면 fail-closed한다.

단순 JWT 검사나 `getUser()` 성공만으로 세션 활성 상태를 판정하지 않는다. 좁은 서버 함수가 매 요청마다 JWT의 session_id에 대응하는 `auth.sessions` 행 존재·user_id 일치·최초 생성시각·설정된 만료와 `staff_session_revocations`의 폐기를 확인한다. 이 조회는 NOLOGIN 소유 보안 정의자 함수로 수행하고 `tm_auth_app`에는 해당 함수의 EXECUTE만 부여한다. 실제 세션 레코드가 없거나 조회가 실패하면 거부한다. 런타임에는 Auth 원본 테이블을 직접 읽거나 수정할 권한을 주지 않는다. 2명 규모에서는 이 검증 비용보다 즉시 차단을 우선한다. 직원 활성 상태 역시 요청마다 DB에서 읽고 허용 결과를 장기 캐시하지 않는다.

### 5.2 쿠키·갱신·폐기

- access/refresh 세션 값은 서버 전용 `Secure`, `HttpOnly`, `SameSite=Lax`, host-only 쿠키에만 저장한다. 브라우저 JS·localStorage·URL·응답 JSON에는 반환하지 않는다.
- 서버에서만 refresh를 수행하고 회전된 쿠키를 함께 갱신한다. 동시 요청·refresh 재사용·만료 실패를 테스트하며 실패 시 쿠키를 지우고 재로그인을 요구한다.
- 앱 세션의 절대 수명은 `auth.sessions.created_at`의 최초 로그인 기준 최대 8시간으로 제한한다. refresh의 JWT iat나 쿠키 재발급 시각으로 연장하지 않는다. 공급자 만료가 더 이르면 그 시점을 따른다. 이는 제품 보안 정책이며 Supabase 기본값 주장과 다르다.
- 로그아웃은 CSRF가 보호된 POST로 처리한다. 검증된 사용자·session_id의 서버측 폐기 기록을 먼저 확정한 뒤 공급자 세션 폐기와 쿠키 삭제를 수행한다. 공급자 폐기 실패는 재시도하며 서버측 폐기는 유지한다. 폐기 기록을 확정하지 못하면 성공을 반환하지 않는다. 비활성 직원과 폐기된 세션은 다음 요청부터 거부한다.
- 세션 폐기 기록에는 session_id, auth_user_id, revoked_at, 원래 세션의 절대 만료일만 저장하고 토큰은 저장하지 않는다. 절대 만료 후 제한된 maintenance가 정리한다.
- 최초 두 계정의 생성·복구는 창업자 런북으로 처리한다. 운영 UI에 공개 초대 기능은 만들지 않는다. 직원 관리 함수는 마지막 활성 Admin 제거·자기 권한 상승을 거부한다.
- 인증·운영자 응답은 `Cache-Control: private, no-store`로 CDN/브라우저 공유 캐시에서 제외한다.
- 상태 변경 요청은 정확한 Origin 검사와 세션 결합 CSRF 토큰을 모두 요구한다. 인증에 성공해도 query 키나 `actor_member_id`를 권한으로 사용하지 않는다.

## 6. 최소 운영자 기능

00B의 화면은 로그인, 마스킹된 리드 목록/상세, Admin 연락처 열람·삭제, Reviewer QA 의견, 로그아웃과 제한된 준비상태 확인에 한정한다. 고객 업무 워크벤치는 04 영역이다.

| 작업 | Admin | Reviewer |
|---|---|---|
| 승인된 마스킹 조회 | 허용 | 허용 |
| 원본 연락처 열람 | 고정 사유 코드와 감사 이벤트가 성공한 전용 함수만 | 거부 |
| 내부 QA 의견 | 추가만 허용 | 추가만 허용 |
| 베타 리드 삭제 요청 | 허용 | 거부 |
| 보유기간 연장 | 00에서 미제공 | 거부 |
| 직원 상태·운영 구성 | 지정된 좁은 함수/배포 런북 | 거부 |
| 고객 데이터 변경·정산 릴리스 | 후속 명세 전 미제공 | 거부 |

QA 의견은 별도 append-only 테이블에 짧은 내부 의견과 상태 코드만 남긴다. 연락처·원문 개인정보 입력 금지를 UI에 안내하고, 서버와 DB에서 의견 길이·상태 코드 allowlist를 함께 검증한다. 클라이언트 입력 제한만 신뢰하지 않으며 길이 검사만으로 모든 개인정보를 탐지한다고 주장하지 않는다. 정정은 새 의견으로 남기며 실제 고객 내용 승인이나 정산 잠금을 대신하지 않는다.

Admin에게 원본 lead 테이블 SELECT를 주지 않는다. 원문 열람 함수는 staff 권한과 사유를 검증하고 감사 이벤트를 기록한 뒤 결과를 반환한다. 감사기록 실패 시 열람도 실패한다. Reviewer 조회에는 원문이 DB 결과·API JSON·HTML 어디에도 없어야 한다.

## 7. 베타 신청·동의·보유·삭제

### 7.1 입력과 저장

00의 공개 신청은 연락 수단 1개(이메일 또는 전화번호), 명시적 동의 여부, 정책 버전만 받는다. 생성/동의 시각·삭제 예정일·분류·source는 서버가 기록한다. 이름, 여행명·일정·목적지·고충 자유입력·계좌·영수증·임의 metadata는 00에서는 받지 않는다. 기존 랜딩 입력도 이 계약에 맞춘다. 가격 의향·영업 상태 추적은 01/04에서 별도 정의한다.

- 연락 수단 종류·길이·형식을 검증하고 모르는 필드는 거부한다. 동의 체크는 기본 해제다.
- `policy_version`, `accepted_at`, `created_at`, `retention_until`, `data_class=real`이 없는 실리드는 DB 함수가 거부한다.
- 서버의 현재 정책 버전과 요청 버전이 다르면 갱신 후 재동의를 요구한다. 과거 데모 행에 동의를 소급 생성하지 않는다.
- 원본 IP·User-Agent·Referer·요청 본문은 앱 DB와 로그에 저장하지 않는다. 호스팅/Auth/이메일 공급자의 별도 로그도 데이터 맵과 보유 설정에 포함한다.
- 성공 응답은 DB 커밋 확인 후에만 반환한다. Production에 메모리 fallback·가짜 성공을 두지 않는다.
- 정확한 same-origin 요청만 허용하고 wildcard CORS를 제거한다. 로그인·접수 rate limit은 요청 간 공유되는 저장/제공자 제어를 사용한다. 서버리스 프로세스 메모리만으로 제한했다고 간주하지 않는다.
- rate limit용 연결 가능 키가 필요하면 원본 IP 대신 회전 HMAC을 사용하고 최대 24시간 후 삭제한다. 제한 저장소 장애 시 신규 접수는 503으로 닫는다.

### 7.2 보유기간

00의 `retention_until`은 최초 `created_at + 30일`로 고정한다. 운영자의 조회·제안·상태 변경으로 연장하지 않는다. 이후 결제 고객의 정책 전환은 01에서 승인된 절차로만 추가한다. 이 30일은 법정 보존기간 확정이 아닌 승인된 최소화 정책이다.

만료 시점 이후에는 모든 제품 조회에서 즉시 제외한다. 삭제 작업은 매시간 실행하며 다음 실행 전 기한에 도달할 행도 선제 처리해 정상 운영에서는 30일을 넘기지 않는다. 작업 지연·저널 실패·삭제 실패는 미완료로 표시하고 경보를 발생시킨다. 마지막 성공 실행이 1시간보다 오래되면 신규 접수를 닫고 운영자가 복구한다. 이미 만료된 행의 조회 차단과 삭제 작업은 접수 플래그에 관계없이 유지한다.

본인 삭제 요청은 공개된 권리행사 연락 경로로 받고, 운영자는 기존 연락 수단의 통제 확인 후 Admin 삭제 요청을 생성한다. 00에서 별도 고객 계정·새 민감 신분증 수집을 만들지 않는다. 요청 접수와 삭제 완료는 구분하며 원본 DB 삭제·외부 저널 확인 전에는 완료라고 답하지 않는다.

## 8. 삭제 저널과 복구 후 재삭제

삭제 요청 상태는 `pending → journaled → purged → completed`이며 각 단계는 재시도 가능·멱등이다. 실패 시 원인 코드와 재시도 상태를 남긴다.

1. 삭제 대상의 불변 UUID·종류를 확정한다.
2. DB와 분리된 pepper로 `entity_type + immutable_uuid`의 HMAC-SHA-256을 만든다. 연락처 HMAC으로 이후 동일 연락처의 새 신청까지 삭제하지 않는다.
3. DB 백업 복구에 영향받지 않는 외부 append-only 저널에 삭제 intent를 쓰고 durable 확인을 받는다.
4. DB에서 해당 리드·연결 QA 의견·정책 동의의 원문 및 불필요한 연결 정보를 트랜잭션으로 삭제한다.
5. 저널에 완료 이벤트를 추가한다. 완료 기록 실패는 재시도하며 기존 intent만으로도 복구 시 재삭제한다.

외부 저널이 실패하면 제품 조회는 차단할 수 있지만 durable intent 없이 삭제 완료로 처리하지 않는다. 복구에서는 pending intent와 completed intent를 모두 재적용한다. intent 이후 DB 삭제 전 장애, DB 삭제 이후 완료 이벤트 전 장애를 각각 검증한다.

저널은 무작위 이벤트 ID, subject_hmac, key_version, 데이터 종류, intent/complete, 시각, 만료일만 가진다. 원본 UUID·연락처·JWT·DB 자격정보를 넣지 않는다. HMAC과 직원 UUID는 익명정보가 아니라 접근 제한된 가명 보안정보로 취급한다.

해당 데이터를 포함할 수 있는 모든 백업 중 **가장 늦은 만료일 + 7일**까지 tombstone과 pepper 버전을 유지한다. 삭제 완료 시점까지의 모든 관련 백업이 최대 35일 안에 만료되면 완료 시점 기준 기본 보수 상한은 42일이며, 실제 manifest로 더 짧게 줄일 수 있다. pending intent는 시간 경과만으로 만료시키지 않는다. 삭제가 지연되어 새 백업이 원문을 포함하면 manifest에 따라 만료일을 재계산한다. 삭제 완료·관련 백업 전부 만료·7일 유예를 확인한 저널만 별도의 제한된 만료 주체가 정리한다. 운영 계정은 수정·삭제할 수 없다.

### 8.1 외부 보관소의 실행 전제

이 문서는 특정 신규 저장소 구매를 승인하지 않는다. 00C 실행 전 창업자는 사용할 외부 암호화 보관소와 리전·보유/삭제 설정·비용을 확정해야 한다. 구현 계획은 provider adapter와 합성 계약 테스트를 분리하되, 실제 durable 저장·조회·만료 증거가 없으면 00C 완료로 판정하지 않는다.

필수 계약은 애플리케이션 DB와 다른 복구 수명주기, 암호화, append-only 권한, writer와 복구 reader/만료 주체 분리, 이벤트 중복 처리, 무결성 확인, 최신 저널 조회와 pepper 복구 가능성이다. 같은 DB의 tombstone 테이블만으로 이 계약을 충족했다고 간주하지 않는다.

## 9. 감사로그·오류·진단

기존 임의 JSON `audit_events.payload`를 신규 보안 감사 계약으로 그대로 사용하지 않는다. 타입화된 allowlist 이벤트로 요청 ID, 가명 직원 ID, 역할, 작업 코드, 대상 종류/필요한 HMAC, 데이터 등급, 결과, 상태 코드, 지연시간만 남긴다.

- 연락처·이름·계좌·세션·공유 토큰·쿠키·연결문자열·영수증 URL·요청/응답 본문·SQL 원문을 로그에 남기지 않는다.
- 운영 로그 최대 90일, rate limit 키 최대 24시간, tombstone은 8절의 백업 연동 만료를 적용한다.
- 운영 계정은 append만 가능하다. 보유기한 이후 삭제는 제한된 maintenance 주체만 수행한다. append-only를 영구 보관으로 해석하지 않는다.
- 클라이언트 오류는 일반화된 메시지·오류 코드·요청 ID만 반환한다. 인증 없음 401, 권한 부족 403, 금지 데모 표면 404, 유효성/정책 버전 오류 400/409, rate limit 429, 안전 구성/공급자 장애 503을 구분한다.
- 공개 health는 DB 종류·프로젝트·스키마·환경변수·예외 메시지를 반환하지 않는다. 상세 readiness는 인증된 제한 진단 또는 배포 검증에서만 본다.
- 계정/세션·개인정보 응답은 no-store, 인증·운영자 페이지는 referrer 제한과 적절한 보안 헤더를 적용한다.
- 합성 민감 문자열을 입력·예외·하위 의존성 오류에 주입하고 로그/오류 응답에서 검출되지 않는지 테스트한다.

## 10. CI와 자동검증

Node.js 22를 00의 검증 런타임으로 고정한다. `npm ci`로 lockfile을 재현하고 GitHub Actions에 다음 required check를 연결한다. PR 검증에는 Production 자격정보를 전달하지 않으며 비신뢰 PR에 write token을 제공하지 않는다.

High/Critical 런타임 취약점과 비밀정보 발견은 기본 병합/출시 차단이다. 문서 생성 전용 `docx`·`pptxgenjs`는 실제 사용처를 확인해 런타임 경로에서 분리한다. 단순히 devDependencies로 이동해 위험이 사라졌다고 주장하지 않으며 개발·CI 도구 위험도 별도로 검토한다. 해결 불가능한 의존성 예외만 advisory, 영향 경로, 보완통제, 담당자, 만료일을 적고 창업자 승인을 받는다. 기존 5 High를 영구 baseline 허용 목록으로 등록하지 않는다.

DB 테스트는 HTTP 거부뿐 아니라 각 역할 DSN으로 직접 시도한다. raw table SELECT, raw 연락처 view 우회, DDL, SET ROLE, 권한 없는 함수, 분류 변경, cross-trip 관계, Reviewer UPDATE/DELETE, 감사로그 변조가 거부되어야 한다.

## 11. 백업·복구 훈련

### 11.1 백업 정책

- 데모 초기화 전 논리 덤프와 스키마 버전·행 수·체크섬을 보관한다. 덤프는 암호화하고 저장소·AI 프롬프트·일반 CI artifact에 넣지 않는다. 복구 검증 후 폐기하며 최대 14일을 넘기지 않는다.
- 실제 데이터 운영은 제공자 백업과 독립 암호화 논리 백업을 함께 사용한다. 현재 Supabase 요금제·백업 가용성을 확인하기 전 자동 백업이 있다고 가정하지 않는다.
- 독립 논리 백업은 매일, 기본 14일 보관한다. 제공자 백업을 포함한 어떤 복구 가능한 사본도 상위 명세의 최대 35일을 넘지 않게 확인한다.
- 실제 제공자 백업이 없거나 독립 보관·만료를 입증하지 못하면 실데이터 접수를 열지 않는다. 요금제 변경·신규 구매는 창업자 별도 승인 사항이다.
- 백업 manifest에 생성/만료일, 스키마 버전, checksum, 암호화 확인, 보관 위치 식별자, 포함 범위를 기록한다. 비밀번호·복호화 키는 manifest/덤프와 분리한다.
- 제공자 DB 백업에 커스텀 역할 비밀번호가 포함된다고 가정하지 않는다. 복구 후 별도 비밀관리 절차로 재설정하고 역할 grants를 검증한다.
- DB 백업은 Storage 객체 백업이 아니다. 00에는 고객 영수증 Storage를 만들지 않으며, 02에서 객체·OCR 공급자 사본의 복구/삭제를 별도로 설계한다.

### 11.2 복구 프로토콜

첫 접수 전 합성 데이터로 1회, 이후 매월 및 주요 스키마 변경 후 훈련한다. 최초 훈련은 빈 DB에서 만든 덤프의 존재 확인으로 대체하지 않는다. 삽입·수정·삭제가 포함된 합성 데이터와 삭제 전 백업을 사용한다.

1. 접수·외부 트래픽을 닫고 복구 담당자와 범위를 기록한다.
2. 대상 백업·최신 외부 저널·필요한 pepper와 복호화 키의 가용성·무결성을 확인한다.
3. 별도 접근 제한 임시 DB/복구 프로젝트에 복원한다. 실제 데이터 백업은 합성 Preview DB로 복원하지 않는다.
4. 복원 직후, 마이그레이션·환경·권한·세션을 바꾸기 전에 백업 manifest의 스키마 버전·테이블·열 집합을 기준으로 행 수·canonical checksum을 검증한다.
5. 최신 마이그레이션, DB 환경 식별자, 커스텀 역할 비밀번호·권한을 재설정한다. 기존 직원 세션은 재로그인 대상으로 처리하고, 마이그레이션 변환 후 기대 결과를 원본 백업 검증과 별도로 확인한다.
6. pending/completed 삭제 intent 전체를 재적용한다. 삭제된 대상 0건, 보존 대상 일치, 신규 동일 연락처의 다른 UUID가 보존되는지 검증한다.
7. 만료 데이터 정리, 역할별 직접 거부 테스트, 설정/로그 카나리를 실행한다.
8. 재삭제 후의 기대 행 수·checksum과 비교하고 창업자가 증거를 확인한 뒤에만 트래픽 재개를 승인한다.
9. 임시 환경·복사본을 정리하고 정리 완료/예외를 기록한다.

저널 최신성·무결성·pepper·키·백업 만료를 입증하지 못하면 복구 DB를 외부에 열지 않는다. 재삭제 전 복구본을 새 운영 백업으로 편입하지 않는다. 데이터 복구 목표는 일일 백업 기준 최대 24시간 손실을 전제로 시작하며, 실제 복구시간을 측정한다. 이 값은 서비스 보장 SLA가 아니다. 받아들일 수 없는 손실/복구시간이 측정되면 접수 전에 백업 주기·PITR 필요성을 재승인받는다.

### 11.3 필수 증거

환경/배포/commit 식별자, 백업 manifest, 스키마 버전, 복구 전후 행 수·checksum, 권한 거부 결과, 저널 재적용 결과, 시작·종료·복구시간, 키 재설정 확인, 임시 환경 폐기 결과, 실행자와 창업자 승인으로 evidence bundle을 만든다. 저장소에는 비식별 요약만 기록한다.

## 14. 사실·설계 정책·외부 전제의 구분

기술 사실은 2026-09-02 공식 자료로 확인했다.

- Supabase 매직링크는 일회성이며, 자동 signup을 막으려면 `shouldCreateUser:false`를 지정해야 한다. 서버에서 token_hash를 세션으로 교환하는 흐름과 허용 redirect 설정을 제공한다. [공식 이메일 로그인 문서](https://supabase.com/docs/guides/auth/auth-email-passwordless)
- Supabase는 JWT 검증에 공식 클라이언트/검증 라이브러리를 권장하고 프로젝트별 JWKS를 제공한다. JWKS는 비대칭 signing key 전제이며 단순 decode는 검증이 아니다. [공식 JWT 문서](https://supabase.com/docs/guides/auth/jwts)
- JWT claims 검증과 서버 세션 유효성 확인은 같지 않다. session_id는 실제 `auth.sessions` 행과 대조할 수 있다. 기본 브라우저 공유 세션 예제를 그대로 쓰지 않고, 이 설계는 서버만 토큰을 다루는 별도 구조를 선택한다. [공식 세션 문서](https://supabase.com/docs/guides/auth/sessions), [공식 서버 인증 설명](https://supabase.com/docs/guides/auth/server-side/advanced-guide)
- DB 백업 가용성은 요금제에 의존한다. 커스텀 역할 비밀번호·Storage 객체는 DB 백업에 포함되지 않으므로 별도 취급이 필요하다. [공식 백업 문서](https://supabase.com/docs/guides/platform/backups), [논리 백업·복원 절차](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
- CHECK OPTION은 자동 갱신 가능한 view의 쓰기를 제한한다. 복합 join view를 같은 방식으로 보호할 수 있다고 일반화하지 않는다. [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)

30일/90일/14일/35일, 8시간 세션, 매시간 삭제, 일일 백업, 월별 복구와 46~64시간 추정은 이 설계의 정책·가정이다. 법정 기간이나 공급자의 기본 설정값으로 주장하지 않는다.

실행 전에 확인할 외부 전제는 두 직원 Auth 등록값, 실제 Supabase 요금제·리전·비대칭 키·custom role 연결 호환성, 배포 환경별 비밀관리, 외부 백업/저널 보관소, 요청 간 공유되는 rate limit 수단, 개인정보 전문 검토·정책 문구다. 확인되지 않은 값은 채워 넣어 사실처럼 표시하지 않고 관련 실행/출시 게이트를 닫아 둔다.
