# TripMoney 유료 콘시어지 → 반복 주최자 사업화 설계

- 작성일: 2026-08-26
- 설계 상태: 대화형 설계 3개 섹션 승인 완료, 작성본에 대한 사용자 명시 승인 대기
- 실행 모델: 1인 창업자/개발자 + Codex + Claude
- 조사 근거: `docs/research/2026-08-25-tripmoney-market-evidence.md`
- 적용 저장소: TripMoney MCP/Web 알파

## 1. 문서 목적

이 문서는 현재 TripMoney 알파를 실제 고객에게 판매할 수 있는 유료 콘시어지 서비스로 전환하고, 반복 주최자의 유료 수요가 확인된 경우에만 최소 B2B2C 제품으로 확장하기 위한 상위 설계를 고정한다.

이 문서가 결정하는 것은 다음과 같다.

- 누구에게 어떤 결과를 얼마에 판매하는가
- 유료 여행 한 건이 접수부터 삭제까지 어떻게 완료되는가
- 기존 코드에서 무엇을 유지하고 무엇을 단계적으로 교체하는가
- 정산·OCR·환율·공유·개인정보의 신뢰 경계를 어디에 두는가
- 1인 실행 체제에서 Codex와 Claude를 어떻게 분리해 사용하는가
- 12주 동안 어떤 근거로 진행·수정·중단을 판단하는가

이 문서는 구현 코드가 아닌 상위 charter다. 작성본이 사용자에게 승인되기 전에는 하위 spec, 구현 계획이나 코드 변경으로 넘어가지 않는다. 승인 후에도 22절의 영역별 하위 spec 승인 게이트를 지킨다.

## 2. 근거와 해석의 경계

### 2.1 확인된 사실

- 2025년 한국인 해외관광 출국은 29,550,177회다. 이는 고유 사용자 수가 아니라 출국 이벤트 수다.
- 국민여행조사의 2025년 해외여행 경험률은 21.5%이며, 만 15세 이상 모집단에 적용한 경험자 근사치는 약 9.98백만 명이다.
- 2025년 해외여행 동행 인원은 본인 포함 평균 3.8명이고 1인 여행 비중은 4.4%다.
- Splitwise·Tricount·TravelSpend·Wanderlog 등은 정산·다통화·여행예산의 높은 무료 또는 유료 경쟁 기준선을 형성한다.
- 카카오뱅크는 이미 `AI 모임총무`를 제공한다.
- TripMoney의 한국 유료 전환율, CAC, 정산 문제 발생률, OCR 실사용 정확도와 반복 사용률은 공개 근거로 확인되지 않는다.

### 2.2 계산하지 않는 값

- 출국 이벤트 29.55백만을 잠재 사용자 29.55백만 명으로 표현하지 않는다.
- 경험자 추정치와 평균 동행 인원을 결합해 공식 그룹 수를 만들지 않는다.
- 개인 평균 지출과 평균 동행 인원을 곱해 공식 그룹 평균 지출을 만들지 않는다.
- 경쟁사 스토어 가격을 TripMoney의 결제 의향 증거로 사용하지 않는다.

### 2.3 설계 가설

- 첫 검증 고객과 2·4·6주차 게이트의 분모는 한국어를 사용하는 20~39세 친구 해외여행 총무다. 다른 성인은 대기목록에 둘 수 있지만 초기 게이트 표본에는 섞지 않는다.
- 초기 운영 코호트는 3~8명으로 제한한다. 이 범위는 공식 시장 구간이 아니라 운영 실험 범위다.
- 총무는 계산기보다 정확성 확인, 누락 탐지, 수정 이력, 최종 공유 결과에 돈을 낼 가능성이 있다.
- 완전 셀프서비스보다 사람 검수를 포함한 유료 콘시어지가 결제 의향과 실제 오류를 더 빨리 학습한다.
- 반복 주최자는 일반 소비자보다 재사용 가능성이 높지만, 유료 증거가 나오기 전에는 조직 제품을 만들지 않는다.

## 3. 목표와 비목표

### 3.1 12주 목표

1. 유료 해외여행 정산 5~10건을 안전하게 완료한다.
2. 적어도 한 가격 셀에서 완전원가 공헌이익이 0원 이상인지 확인한다.
3. 정산 오류, OCR 수정, 환율 이견, 사람 작업시간과 고객 이의를 100% 기록한다.
4. 서로 다른 반복 주최자 고객 2명 이상으로부터 실제 유료 파일럿 결제를 확보한다.
5. 반복 수요가 확인된 경우에만 최소 조직·템플릿·주최자 흐름을 제공한다.

### 3.2 명시적 비목표

- 공개 셀프서비스 B2C 대규모 출시
- iOS·Android 네이티브 앱
- 카카오톡 자동 단체방 봇
- 카드·은행 거래내역 자동 수집
- 자동송금·자동출금·환전·공동지갑·회비 수납
- OCR 또는 AI 결과의 무검수 자동 확정
- 지도·예약·일정 추천 중심의 여행 슈퍼앱
- 앱스토어 구독과 복잡한 구독 청구
- 화이트라벨, SSO, 여행사 ERP·CRM·재고관리
- 해외 언어·해외시장·국내 범용 모임총무
- 반복 고객 근거가 없는 조직 멀티테넌시 선행 구축
- 11개 MCP 도구 전체를 한 번에 재작성하는 대규모 리팩터링

## 4. 고객과 유료 오퍼

### 4.1 첫 고객 적격 조건

모든 조건을 만족해야 2·4·6주차 게이트를 판정하는 초기 유료 코호트에 포함한다.

- 한국어로 상담할 수 있는 20~39세 성인 여행 총무
- 친구 중심 3~8명 해외여행
- 여행이 이미 끝났거나 여행 종료와 필수 자료 완성이 접수 후 7일 이내로 확정됨
- 총무가 멤버별 결제자·참여자·통화·영수증을 확인할 수 있음
- 참여자가 읽기 전용 결과를 확인할 수 있음
- 고객 자금이 TripMoney를 통과하지 않는 흐름에 동의함

위 조건에는 맞지만 자료 완성이 8~60일 뒤인 고객은 대기목록으로만 받는다. 유료 게이트의 결제·완료 분모에는 포함하지 않는다.

초기 코호트에서 제외한다.

- 미성년자가 직접 계약·결제하는 여행
- 9명 이상 단체, 공개 모집형 패키지, 불특정 다수 여행
- 법인 출장비·세금 증빙·회사 회계 승인이 필요한 사례
- 해외송금 또는 외국 은행 계좌 송금이 필수인 사례
- 카드·은행 자동연동 또는 TripMoney의 자금 보관을 요구하는 사례
- 여행 종료 후 60일을 넘긴 대량 사후 복구 사례

### 4.2 가격 셀

| 상품 | 고객 표시 가격 | 범위 | 초안 SLA | 수정·참여자 지원 |
|---|---:|---|---|---|
| 검수형 | 29,000원/여행 | 최대 5명·30건 | 완전한 자료 접수 후 48시간 | 수정 묶음 1회, 참여자 배포는 총무 수행 |
| 마감 대행형 | 59,000원/여행 | 최대 8명·80건 | 완전한 자료 접수 후 24시간 | 수정 묶음 2회, 응답 추적·총무가 보내는 1회 알림 문구 지원 |

- 가격은 고객이 실제 결제할 최종 금액으로 표시한다. 세금계산·영수증과 공헌이익에서는 사업자의 실제 과세 지위에 따른 공급가액과 납부 대상 부가세를 분리한다.
- SLA 시계는 결제와 필수 자료 체크리스트가 모두 완료된 시점에 시작한다.
- 고객 답변을 기다리는 동안 SLA 시계는 일시 정지하고 상태 이벤트에 사유를 기록한다.
- 24·48시간 SLA의 종료점은 총무가 승인할 수 있는 정산 초안 전달이다. 총무 승인 대기, 참여자 검토와 이의 해결 시간은 SLA에서 제외하되 별도 소요시간으로 측정한다.
- 총무 승인 후 모든 상품에서 24~72시간의 참여자 검토창을 연다. 무응답은 승인이 아니며 `not_responded`로 기록한다. 검토창이 끝나고 미해결 이의가 없을 때 총무가 최종 잠금을 요청할 수 있다.
- 최종 결과는 검토창 종료 또는 마지막 이의 해결 중 늦은 시점부터 1영업일 안에 전달한다.
- `수정 1회`는 동일 정산 버전에 대해 고객이 한 번에 모아 제출한 변경 요청 묶음 하나를 뜻한다.
- 범위를 초과한 여행은 자동으로 받지 않고 마감 대행형 재견적 또는 정중한 거절로 처리한다.
- 최종 잠금 전 고객이 취소하면 전액 환불한다.
- 최종 잠금 후 중대한 금액 오류를 1영업일 안에 수정하지 못하면 전액 환불한다.
- 환불·PG·OCR·저장비와 사람 원가는 모든 공헌이익 계산에 포함한다.

가격과 한도는 시장 사실이 아닌 검증용 가설이다. 구두 의향, 폼 선택과 결제 직전 이탈은 매출로 계산하지 않는다.

### 4.3 결제 구현과 외부 선행조건

- 첫 PG 구현 대상은 Toss Payments 결제창형 웹 결제다.
- 주문번호는 TripMoney가 생성하고, 서버가 저장한 주문번호·금액과 성공 URL의 값을 대조한 뒤 서버에서 결제를 승인한다.
- 승인·취소 요청에는 고유 멱등키를 사용하고 `paymentKey`, `orderId`, 공급자 상태를 보존한다.
- Toss 일반 결제 웹훅에 서명 헤더가 있다고 가정하지 않는다. `tosspayments-webhook-transmission-id`와 payload digest로 중복을 차단하고, 상태를 바꾸기 전에 서버가 Toss 조회 API로 결제를 다시 조회해 저장된 `orderId`, `amount`, `paymentKey`와 상태를 대조한다.
- 테스트 키와 sandbox로 전체 흐름을 검증하되 프로덕션 MID와 카드사 심사가 완료되기 전에는 `PAYMENTS_ENABLED=false`를 유지한다.
- 사업자등록, 통신판매업 적용 여부, 판매자 표시, 약관·개인정보·환불정책과 PG 가맹 준비가 끝나기 전에는 실제 결제를 받지 않는다.
- 개인 계좌 송금을 유료 전환의 임시 우회로 사용하지 않는다.
- 위 선행조건이 2주차 시작까지 충족되지 않으면 지불의사 게이트 시계를 멈추고, 결제 없는 인터뷰를 유료 증거로 대체하지 않는다.
- 외부 심사 대기 중에도 합성 데이터 개발은 계속할 수 있지만 후속 유료 게이트를 통과한 것으로 계산하지 않는다. 외부 대기일은 12개 활성 실행 주차에서 제외하고 총 경과일과 함께 보고한다. 4개 달력 주가 지나도 실제 결제 선행조건이 해결되지 않으면 추가 개발보다 판매 방식·사업 준비의 중단 또는 변경을 먼저 결정한다.

구현 근거는 [Toss Payments 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow), [코어 API](https://docs.tosspayments.com/reference), [웹훅 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events), [배포 체크리스트](https://docs.tosspayments.com/guides/v2/deploy-checklist)를 기준으로 한다.

## 5. 서비스 블루프린트

### 5.1 고객 여정

```text
적격성 확인
  → 상품·범위·환불·개인정보 안내
  → TripMoney 서비스 이용료 결제
  → 여행·멤버·지출·영수증 수집
  → OCR 초안과 환율 근거 생성
  → 사람 검수와 누락 확인
  → 총무의 정산 초안 승인
  → 참여자의 읽기·이의 제기
  → 최종 정산 잠금
  → Kakao Share 또는 복사 가능한 정산 결과 전달
  → 송금 완료 여부를 사용자가 수동 표시
  → 만족도·재사용·소개 조사
  → 보유기간 종료 후 자동 삭제
```

### 5.2 주문·콘시어지 케이스 상태

서비스 주문과 실제 수행 케이스는 서로 다른 상태머신이다. 베타에서는 결제가 확인된 주문 하나가 케이스 하나를 만들며, 결제·환불 상태를 수행 상태에 섞지 않는다.

```text
service_order
draft → awaiting_payment
awaiting_payment → paid | payment_failed | cancelled
paid → refund_pending → refunded
```

```text
concierge_case
collecting
  → reviewing
  → awaiting_organizer
  → participant_review
  → finalized
  → delivered
  → closed
```

케이스 보조 상태는 `paused`, `cancelled`, `reopened`다. 결제 전 취소는 주문만 `cancelled`가 되고, 결제 후 환불은 주문의 환불 상태와 케이스 종료 사유를 각각 기록한다. `cancelled` 케이스는 되살리지 않고 새 주문·케이스를 만든다. `closed` 후 보장 범위의 교정은 `reopened` 이벤트와 새 정산 버전을 만들며 기존 이력을 덮어쓰지 않는다. 모든 주문·케이스 상태 변경은 별도 이벤트로 누적한다.

총무 승인, 참여자 결정과 내부 QA는 정산 스냅샷 버전에 각각 귀속한다. 새 버전이 생기면 이전 기록은 보존하되 잠금 효력을 잃는다. 참여자 전원 승인은 잠금 필수조건이 아니지만, 최소 검토창 종료·총무의 해당 버전 승인과 잠금 요청·미해결 이의 0건·창업자 또는 지정 staff의 내부 QA 승인은 필수다. 무응답 수는 최종 결과에 표시한다.

### 5.3 내부 운영 체크포인트

| 단계 | 필수 확인 | 다음 단계 차단 조건 |
|---|---|---|
| 적격성 | 인원·여행 유형·일정·요구 기능 | 초기 범위 밖 고객 |

- 검증되지 않은 Toss 송금 딥링크

### 7.3 실고객과 레거시 경로 격리 불변식

기존 MCP·프로토타입은 합성 데모 전용으로 유지한다. 유료 케이스는 생성 시부터 `data_class=real`로 표시하고 아래에서 허용한 최소권한 경로 외에는 읽거나 바꿀 수 없다.

| 경로 | 프로덕션 정책 | 허용 데이터·인증 |
|---|---|---|
| `/mcp` | `MCP_DEMO_ENABLED`일 때만 열림 | `data_class=demo`만, 전역 키가 없으면 항상 503 |
| `/api/web` | 레거시 데모 API, 단계적 폐기 | `data_class=demo`만, URL query 키 금지 |
| `/prototype` | `DEMO_SURFACES_ENABLED`일 때만 열림 | 합성 데이터만, 실데이터 식별자 거부 |
| `/api/beta` | `BETA_LEAD_INTAKE_ENABLED`와 고지 버전이 있을 때만 접수 | 최소 연락처·명시 고지, 여행 금융·영수증 금지 |
| `/checkout/:grant` | 주문별 grant를 서버 세션으로 교환 | 주문 1건, 서버 저장 상품·금액, Origin·CSRF·멱등 검사 |
| `/intake/:grant` | 결제된 케이스별 자료제출 grant | 케이스 1건, 허용 필드·파일 수·크기·MIME, rate limit |
| `/review/:grant` | 총무별 정산 검토 grant | 스냅샷 1개, 초안 조회·총무 승인·잠금 요청만 허용 |
| `/operator` | 실데이터 유일 직원 운영 경로 | Supabase Auth + active staff allowlist |
| `/share/:grant` | 참여자별 제한 조회·결정 | 스냅샷·참여자 1명, 조회·승인·이의·철회만 허용 |
| `/api/webhooks/toss` | 고객 세션 없이 수신, provider 조회 후 처리 | transmission ID 멱등, 주문번호·금액·결제키·상태 재대조 |

- `trips.data_class`는 `quarantined|demo|real`의 NOT NULL 값이며 기본값을 두지 않는다. 기존 행은 전부 `quarantined`로 백필해 모든 제품 경로에서 거부하고, 원본·감사로그를 확인해 합성임이 입증된 행만 운영자가 `demo`로 승격한다.
- 기존 `beta_leads`도 UI·지표에서 격리한 뒤 고지 버전·수집일·보유근거를 점검한다. 근거와 기한을 입증하지 못한 연락처는 삭제하고, 유지 가능한 행만 `real`과 삭제 예정일을 명시한다.
- 레거시 자격정보인 `trips.api_key`, `share_token`, `members.account_no`는 `real` 행에서 DB 제약으로 NULL이어야 한다.
- DB에는 demo·lead·checkout·intake·organizer-review·operator·participant-share·payment-webhook용 최소권한 역할을 분리하고, RLS 또는 `security_barrier` view와 `CHECK OPTION`으로 각 역할의 허용 행·열·함수를 제한한다. 각 어댑터는 별도 DB 자격정보를 사용하며 구성 누락 시 fail-closed한다.
- `/mcp`, `/api/web`, `/prototype`의 모든 조회·변경은 `data_class=demo` 조건을 DB 정책, 데이터 접근 계층과 부정 테스트에서 함께 강제한다. 애플리케이션 입력만 믿지 않는다.
- `/checkout/:grant`는 30분, `/intake/:grant`는 72시간, `/review/:grant`와 `/share/:grant`는 최대 7일 유효한 32바이트 이상 난수 토큰의 해시만 저장한다. URL 토큰은 즉시 더 짧거나 같은 수명의 `Secure`·`HttpOnly`·`SameSite=Strict` 세션으로 교환하고 폐기·재발급할 수 있으며 모든 grant 화면은 `Referrer-Policy: no-referrer`를 사용한다.
- checkout·intake의 상태 변경 POST는 허용 Origin, 세션 결합 CSRF 토큰과 멱등키를 모두 요구한다. intake signed upload URL은 10분만 유효하고 결제된 케이스의 storage prefix 밖에는 쓸 수 없다.
- 신규 checkout 세션은 `REAL_DATA_INTAKE_ENABLED`와 `PAYMENTS_ENABLED`, 신규 intake 세션은 `REAL_DATA_INTAKE_ENABLED`와 `RECEIPT_UPLOAD_ENABLED`가 모두 켜진 경우에만 발급한다. 결제 플래그를 끈 뒤에도 이미 발생한 결제의 유효 웹훅·취소·환불·삭제 요청은 안전하게 처리한다.
- organizer review grant는 `view_draft`, `approve_as_organizer`, `request_lock`만, participant share grant는 `view_summary`, `approve_settlement`, `object_settlement`, `withdraw_objection`만 가질 수 있다. DB 제약으로 actor role과 scope의 교차 조합을 거부한다.
- `/operator`, `/review`, `/share`, `/checkout`, `/intake`, Toss webhook은 레거시 전역 키를 인증으로 인정하지 않는다.
- 고객 영수증과 여행 원장은 개인 메신저·개인 이메일·AI 프롬프트로 받지 않는다. 관리되는 `/intake` 또는 운영자 화면에서 고객과 함께 직접 입력하는 방식만 허용한다.
- 이 격리가 배포·검증되기 전에는 `REAL_DATA_INTAKE_ENABLED`를 켤 수 없다.

## 8. 기술 아키텍처

### 8.1 선택: 모듈형 모놀리스

Vercel + Supabase 기반 단일 배포를 유지한다. 마이크로서비스, 별도 이벤트 플랫폼과 전면 프레임워크 전환은 하지 않는다.

```text
Public Landing / Checkout ─┐
Operator Workbench ────────┼─ HTTP/MCP Adapters
Participant Share ─────────┤          │
MCP Tools ─────────────────┘          ▼
                               Application Services
                              ┌────────┼─────────┐
                       Commercial   Case     Privacy
                       Receipt      FX       Settlement
                       Sharing      Evidence
                              └────────┼─────────┘
                                       ▼
                          Postgres + Private Object Storage
                                       │
                          OCR / FX / PG / Kakao Share
```

영수증 객체 저장소는 기존 Supabase 프로젝트의 private Storage bucket `tripmoney-receipts`를 사용한다. signed upload와 read URL의 유효기간은 10분으로 제한한다. 해당 리전의 국외처리 게이트를 통과하지 못하면 bucket을 만들더라도 실제 고객 업로드 기능은 켜지 않는다.

### 8.2 모듈 경계

| 모듈 | 책임 | 기존 코드와의 관계 |
|---|---|---|
| `lib/commercial/` | 주문·결제·환불·멱등 웹훅 | `betaLeads`에서 유료 상태 분리 |
| `lib/cases/` | 콘시어지 상태·SLA·체크리스트 | `trips`와 주문을 연결하되 동일 개념으로 만들지 않음 |
| `lib/receipts/` | 비공개 업로드·OCR·검수·삭제 | `ocr.ts` 파서를 어댑터로 재사용 |
| `lib/domain/` | 금액·환율·분담·정산 불변식 | `server.ts`·`mcpEngine.ts`에서 사용 경로별 이동 |
| `lib/sharing/` | 초대·scope·만료·폐기 | 단일 `share_token` 대체 |
| `lib/privacy/` | 동의·보유기간·삭제·암호화 | 계좌와 원본 영수증 최소화 |
| `lib/analytics/` | 비식별 이벤트·작업시간·단위경제성 | `metrics` 단순 집계를 증거 원장으로 확장 |
| `api/checkout/` | 제한된 주문 세션·PG 승인·취소 결과 | 서버 저장 주문·금액 외 입력 불신 |
| `api/intake/` | 제한된 케이스 자료제출·signed upload | 운영자 전체 권한과 분리 |
| `api/review/` | 총무의 버전별 초안 승인·잠금 요청 | participant share 권한과 분리 |
| `api/operator/` | 인증된 운영자 API | `api/web.ts`를 점진적으로 대체 |
| `api/share/` | 제한된 참여자 API | 전 여행 데이터 조회 금지 |
| `api/webhooks/` | PG 계약별 인증·조회 대조·멱등 외부 이벤트 | 공개 폼 API와 분리 |

`lib/server.ts`의 11개 도구를 한 번에 옮기지 않는다. 콘시어지에서 실제로 호출되는 여행 생성, 지출·영수증, 정산, 공유 경로부터 공통 서비스를 사용하고 나머지 도구는 회귀 테스트 아래 유지한다.

유료 케이스는 MCP를 통해 생성·운영하지 않는다. 위의 재사용은 검증된 순수 로직과 어댑터 내부 코드에 관한 것이며, 레거시 MCP 인증·저장 경로를 실데이터에 재사용한다는 뜻이 아니다.

8주차 B→C 게이트 전에는 C 단계 테이블명·청구 모델·연락처 저장·비동기 인프라를 확정하지 않는다. 게이트를 통과하면 반복 주최자 인터뷰와 실제 유료 파일럿의 공통 흐름을 입력으로 별도 브레인스토밍, 하위 spec, 사용자 승인을 거친다.

후속 설계가 지켜야 할 경계만 지금 고정한다.

- 조직 운영자, 내부 직원, 비용 분담 참여자는 서로 다른 주체이며 하나의 `members` 테이블에 합치지 않는다.
- 모든 조직 자원은 DB와 API에서 조직 스코프를 강제하고 cross-org 부정 테스트를 갖는다.
- 템플릿에는 원본 영수증·계좌·이전 참여자의 민감정보를 복제하지 않는다.
- 연락처, B2B 청구, outbox는 유료 파일럿에서 필요성이 입증된 것만 설계한다.

## 10. 인증·권한·보안

### 10.1 운영자 인증

- Supabase Auth 매직링크를 사용한다.
- `internal_staff` 허용 목록에 존재하고 `active=true`인 계정만 운영자 API에 접근한다.
- 실제 데이터 API는 URL query 키를 받지 않는다.
- 모든 변경은 인증 사용자 ID, 케이스, 목적과 함께 감사로그에 남긴다.
- 프로덕션에 인증 구성이 없으면 운영자 API와 실제 데이터 접수를 fail-closed한다.

### 10.2 총무·참여자 검토 접근

- 32바이트 이상의 암호학적 난수 토큰을 생성하고 DB에는 SHA-256 해시만 저장한다.
- 링크 토큰은 한 번 서버 세션으로 교환한 뒤 URL에서 제거한다.
- 교환된 세션은 링크보다 오래 살 수 없고 `Secure`, `HttpOnly`, `SameSite=Strict` 쿠키로 제한한다. 공유 화면은 `Referrer-Policy: no-referrer`를 사용한다.
- 총무 review grant는 `view_draft`, `approve_as_organizer`, `request_lock`만 허용하고 snapshot·case·organizer에 결합한다.
- 참여자 share grant는 `view_summary`, `approve_settlement`, `object_settlement`, `withdraw_objection`만 허용하고 snapshot·participant에 결합한다.
- 총무와 참여자 scope는 DB 제약과 API 계약에서 교차 사용할 수 없다. 어느 bearer 토큰으로도 계좌정보를 쓰게 하지 않는다.
- 공유 링크 기본 만료는 7일이며 즉시 폐기할 수 있다.
- 여행·참여자·정산 버전이 일치하지 않으면 접근을 거부한다.
- `members`는 비용 분담 주체이며 인증 ID가 아니다.

### 10.3 계좌정보

- 초기 B 단계와 구현 계획 00~04에서는 계좌번호를 수집·저장하지 않는다. 기존 입력 UI와 Toss 딥링크는 비활성화하고 상대 이름·금액 복사만 제공한다.
- bearer 공유 링크는 신원 증명이 아니므로 `submit_payout` 권한을 부여하지 않는다.
- 계좌 저장이 실제 유료 병목으로 입증되면 별도 하위 spec과 사용자 승인을 받는다. 그 spec은 최소한 사전 검증 연락처에 대한 일회용 코드, 변경 알림, 30분 적용 유예, 총무 재확인, 변경 감사로그와 즉시 삭제를 포함해야 한다.
- 저장을 승인한 경우에만 별도 `member_payout_methods`에 AES-256-GCM ciphertext, unique IV, key_version, last4를 저장하고 키는 DB와 분리한다. AAD에는 trip_id와 member_id를 포함한다.
- 운영자·조직 관리자는 원문을 기본 조회할 수 없고 Kakao 문구, CSV, 분석 이벤트, 애플리케이션 로그에도 원문을 넣지 않는다.

### 10.4 보안 중단 조건

다음 중 하나가 발생하면 신규 유료 접수와 최종 잠금을 즉시 끈다.

- 다른 여행 또는 조직 데이터 접근
- 폐기·만료 토큰 재사용 성공
- 계좌번호·영수증 원본·연락처의 로그 또는 공유 노출
- 승인되지 않은 정산 잠금
- 백업 복구 불가 또는 데이터 무결성 상실

## 11. 금액·환율·정산

### 11.1 금액 표현

- B 단계 기준통화는 KRW로 고정한다.
- 외화 원금은 DB `numeric(20,8)`, TypeScript와 API에서는 정규화된 decimal 문자열로 보존한다.
- 환율은 DB `numeric(24,12)`, TypeScript에서는 decimal 문자열로 다룬다.
- KRW 환산액·분담액·송금액은 DB `bigint`, TypeScript 내부 `bigint`, JSON API의 10진 정수 문자열로 표현한다.
- 양수 외화 금액의 KRW 환산은 정확한 decimal 곱셈 뒤 지출 단위에서 `ROUND_HALF_UP`으로 1원에 반올림한다. 이후 정산에서는 다시 환산·반올림하지 않는다.
- largest-remainder 잔차는 버림 뒤 소수 잔여가 큰 순서, 동률이면 안정적인 `member_id` 오름차순으로 배분한다. 균등 분담처럼 잔여도 같으면 `member_id`만 사용한다. 같은 ID 집합의 입력 순서가 바뀌어도 결과가 같아야 한다.
- 기존 DB `numeric(14,2)`, SQL `::float`, JavaScript `number` 경로는 데모 호환용으로만 남긴다. `0013_money_fx_provenance.sql`에서 신규 정수 원 컬럼을 추가해 dual write·백필·대조한 뒤 실데이터 최종 경로를 전환한다.
- `lib/settlement.ts`는 알고리즘과 레거시 회귀 기준으로 재사용하되 현재 number 구현을 실제 유료 정산에 그대로 호출하지 않는다. 정수 구현과 고정 tie-break 테스트를 먼저 만든다.

### 11.2 환율 출처성

- 환율 공급자, 통화쌍, 기준시각, 조회시각, 원율을 저장한다.
- 캐시가 오래되었으면 사용자와 운영자에게 `stale` 경고를 표시한다.
- 외부 조회 실패 시 출처가 남은 과거 환율 또는 운영자 사유가 있는 수동 환율만 허용한다.
- 환율을 바꾸면 새 정산 버전을 만들고 재승인을 요구한다.

### 11.3 최종 정산 불변식

최종 잠금 전에 모두 만족해야 한다.

- 각 지출의 분담액 합계 = 해당 지출의 KRW 환산액
- 모든 멤버의 net 합계 = 0
- 모든 송금액은 양수 정수 원
- 미상 결제자 또는 미해결 제외 지출 = 0건
- 적용된 expense version과 fx quote가 존재
- 총무의 해당 버전 승인·잠금 요청 완료
- 참여자 이의가 해결 또는 명시적으로 철회됨
- 창업자 또는 지정 staff의 불변식·증빙 내부 QA와 릴리스 승인 완료

총무의 승인은 고객이 정산 내용에 동의하는 행위이고, 참여자 결정은 개인별 확인·이의 행위이며, 내부 QA는 시스템이 잠금 조건과 증빙을 충족했는지 확인하는 운영 행위다. 세 행위는 서로 대체하지 않는다. 시스템은 세 조건과 검토창을 확인한 뒤 스냅샷을 잠근다.

잠긴 `settlement_snapshot`은 변경하지 않는다. 수정은 새 버전을 생성하며 과거 공유 링크는 해당 과거 버전을 계속 가리키거나 명시적으로 폐기된다.

## 12. 영수증 증빙 파이프라인

이 파이프라인을 실데이터에 켜기 전에 11.1의 bigint 원 금액·decimal 환율 저장과 `0013_money_fx_provenance.sql` 전환을 완료한다. 사람 승인으로 생성되는 expense는 레거시 number 컬럼만 가진 상태로 저장할 수 없다.

```text
서명된 private upload
  → 파일 크기·MIME·시그니처 검사
  → EXIF 및 민감번호 마스킹
  → checksum과 보유기한 기록
  → OCR 실행
  → 필드별 추출값·신뢰도 저장
  → 운영자 수정
  → 사람 승인
  → expense 생성
  → 최종 잠금 후 원본 삭제 예약
```

- 임의의 고객 제공 원격 URL을 OCR 서버가 직접 fetch하지 않는다.
- base64 원문을 일반 API 로그에 남기지 않는다.
- 카드번호 전체, CVC, 주민·여권번호를 저장하지 않는다.
- OCR 공급자의 실제 처리 국가·보유·학습·재위탁을 확인하지 못하면 실제 원본을 전송하지 않는다.
- OCR 실패는 수동 입력으로 전환하며 실패 원인과 사람 작업시간을 기록한다.
- OCR 결과만으로 expense를 생성하거나 최종 정산을 잠그지 않는다.
- 모델·API 버전 변경 시 고정 영수증 세트로 회귀 테스트한다.
- 원본, 마스킹·리사이즈 파생물, 공급자 원응답과 필드 추출값은 각각 보유기한과 삭제 상태를 가진다. 공급자 삭제 API 또는 계약상 삭제 증빙을 확인할 수 없으면 실제 원본 OCR을 켜지 않는다.

## 13. 공유와 송금 라스트마일

- Kakao Share는 사용자가 수신자를 직접 선택하는 공유 표면으로만 사용한다.
- 공유 전에 여행명, 정산 버전, 기준 환율, 송금 제안의 미리보기를 제공한다.

- 전체 계좌번호, 영수증 원본과 상세 지출은 메시지에 포함하지 않는다.
- 자동·예약·대량 발송은 하지 않는다.
- 카카오 전송 성공을 정산 승인 또는 송금 완료로 해석하지 않는다.
- 초기에는 상대 이름과 금액 복사를 제공한다.
- 초기 B에서는 참여자 계좌를 받지 않고 상대 이름·금액 복사만 제공한다.
- 자동송금, 비공개 Toss 딥링크와 입금 자동확인은 제공하지 않는다.

## 14. 개인정보·규제 경계

이 설계는 법률 확정이 아니라 보수적 제품 경계다. 실제 데이터·자금 흐름도를 기준으로 전문 검토를 통과하기 전에는 관련 기능을 켜지 않는다.

### 14.1 자금 경계

- TripMoney는 자체 디지털 정산 지원 서비스 이용료만 받는다.
- 회원 간 여행비를 수취·보관·분배하지 않는다.
- 공동지갑, 충전금, 포인트, 선불잔액을 만들지 않는다.
- 실제 송금·출금·환전·해외송금을 실행하지 않는다.
- 은행·카드 거래를 자동 수집하지 않는다.
- 정산 결과는 정보·계산 결과이며 지급 완료 또는 법적 채무 확정을 의미하지 않는다.

### 14.2 국외처리 게이트

- Vercel, Supabase, OCR, PG의 실제 법인·리전·재위탁자·보유기간을 데이터 맵에 기록한다.
- 개인정보보호법상 적용 가능한 국외이전 근거와 해당 고지·동의 요건을 데이터 항목별로 검토한다.
- 근거와 사용자 고지가 준비되지 않으면 실제 개인정보 접수를 차단한다.
- 분석·오류추적에는 이름·계좌·영수증 URL을 전송하지 않는다.

### 14.3 참여자 데이터 최소화와 고지

- 총무에게는 법적 이름 대신 참여자가 알아볼 수 있는 별칭을 먼저 입력하게 하고, 참여자 전화번호·이메일은 수집하지 않는다. 공유 링크 전달은 총무가 직접 수행한다.
- 총무가 타인의 지출·별칭을 제공할 수 있는 권한과 처리 근거, TripMoney가 참여자에게 해야 할 고지 시점은 실제 데이터 흐름도를 기준으로 전문 검토에서 확정한다.
- 그 검토와 고지 문구가 승인되기 전에는 실데이터 수집을 켜지 않는다. 총무의 체크박스 하나를 모든 참여자의 동의로 간주하지 않는다.
- 참여자는 공유 링크의 첫 화면에서 운영자, 목적, 항목, 보유기간, 국외처리, 권리행사 방법을 확인한 뒤 조회를 계속하거나 삭제·이의 경로를 선택한다. 고지 확인은 처리 근거 자체와 구분해 기록한다.

| 데이터 | 기본 삭제 시점 | 예외 |
|---|---|---|
| 미결제 베타 리드 연락처 | 마지막 응답·제안 후 30일 | 삭제 요청 시 즉시, 결제 시 케이스 정책으로 전환 |
| 원본 영수증·마스킹/리사이즈 파생물·OCR 원응답 | 최종 잠금 후 7일 | 사용자 조기 삭제, 공급자 사본 포함 |
| 교정된 OCR 필드·여행 원장·정산·참여자 별칭 | 케이스 종료 후 30일 | 분쟁 중에는 접근 제한 후 분쟁 종료일부터 30일 이내 삭제 |
| 계좌 지급정보 | 초기 B에서는 수집하지 않음 | 후속 승인 시 케이스 종료 후 최대 30일 |
| 취소·환불·중도 이탈 케이스 데이터 | 환불·분쟁에 필요한 처리가 끝난 뒤 7일 | 서비스 결제 기록은 아래 별도 기준 |
| 케이스 연결 제품 이벤트 | 케이스 종료 후 30일 안에 삭제 또는 집계와 연결 해제 | 연결 전에는 익명이 아니라 가명정보로 취급 |
| 운영·보안 감사로그 | 생성 후 최대 90일 | 사고·법적 보존 필요 시 접근 제한과 사유·종료일 기록 |
| 비식별 집계 지표 | 식별·연결 가능성을 제거한 뒤 유지 | 재식별 가능한 소규모 셀은 삭제 |
| 서비스 결제 기록 | 법령·PG 계약이 요구하는 기간 | 여행 원본·계좌와 분리 보관 |
| 암호화 백업 | 최대 35일 또는 더 짧은 공급자 설정 | 이 상한을 확인·설정할 수 없으면 실데이터 기능을 켜지 않음 |

- 삭제 완료 시 DB와 분리된 pepper로 만든 HMAC-SHA-256 tombstone과 `key_version`을 `가장 오래된 백업 만료일 + 7일`까지 유지한다. 단순 해시나 원문 식별자는 저장하지 않는다. 해당 pepper 버전은 마지막 관련 백업과 tombstone이 모두 만료될 때까지 폐기하지 않는다.
- 백업 복구 리허설과 실제 복구에서는 외부 트래픽을 열기 전에 tombstone을 재적용하고 DB, 객체 저장소, OCR 공급자 사본을 다시 확인한다.
- 애플리케이션·접근로그·오류추적의 보유기간도 위 범위를 넘지 않도록 공급자 설정과 삭제 작업에 포함한다.

여행 템플릿 재사용은 원본 여행을 복사하지 않는다. 일정 구조, 카테고리와 분담 규칙만 고객의 별도 선택으로 저장한다.

## 16. 사용자 표면

### 16.1 공개 랜딩

- `여행 총무 AI`보다 `근거가 남는 해외여행 최종 정산`을 중심으로 카피를 수정한다.
- 29,000원·59,000원 두 가격 셀을 명확히 표시한다.
- `3~8명`은 운영 범위로 표시하고 시장 통계처럼 표현하지 않는다.
- 신청 전 적격·제외 조건, SLA, 환불과 돈을 보관하지 않는다는 점을 표시한다.
- 결제 전 약관·개인정보·국외처리 고지로 연결한다.

### 16.2 운영자 워크벤치

- 주문 큐와 SLA
- 자료수집 체크리스트
- 영수증 원본·OCR·수정·승인 비교
- 환율 출처와 수동 사유
- 정산 버전·불변식·이의·잠금
- Kakao 미리보기·링크 폐기
- 작업시간·비용·환불
- 보유기간·삭제 요청·사고중단 스위치

기존 `/prototype`은 합성 데이터 데모로 유지한다. 직원의 실데이터 운영은 인증된 `/operator`만 사용하고, 고객은 주문·케이스·스냅샷 하나로 제한된 `/checkout`, `/intake`, `/review`, `/share` 경로만 사용한다. Toss webhook은 조회 대조 후 결제 상태만 처리한다.

### 16.3 총무 검토

- `/review/:grant`에서 결합된 한 스냅샷의 전체 초안·근거·수정 이력을 본다.
- 해당 버전을 승인하거나 수정 요청을 제출하고, 참여자 검토창 종료·미해결 이의 0건 뒤 잠금을 요청할 수 있다.
- 총무 grant로 내부 QA를 승인하거나 다른 케이스·버전을 보거나 참여자 행위를 대신할 수 없다.
- 승인·잠금 요청은 grant, snapshot, organizer, 시각과 함께 감사로그에 남긴다.

### 16.4 참여자 공유

- 가입 없이 제한된 토큰 세션으로 접근한다.
- 본인의 paid·owed·net과 자신이 관련된 송금만 우선 표시한다.
- 환율 기준, 반올림, 원본 존재 여부와 마지막 수정시각을 볼 수 있다.
- 승인, 이의 제기와 이의 철회만 허용한다. 계좌정보 입력은 별도 신원확인 설계 전에는 제공하지 않는다.
- 다른 참여자의 계좌와 영수증 원본은 볼 수 없다.

## 17. 지표와 증거 원장

### 17.1 핵심 퍼널

```text
qualified_lead
  → offer_sent
  → checkout_started
  → paid
  → materials_complete
  → draft_ready
  → organizer_approved
  → participant_viewed
  → finalized
  → delivered
  → repeat_or_referral
```

각 이벤트는 분모를 알 수 있어야 하며 PII를 넣지 않는다.

### 17.2 단위경제성

두 값을 동시에 계산한다.

```text
순매출
= 실제 결제액 - 취소·환불 - 실제 과세 지위에 따른 납부 대상 부가세

현금 공헌이익
= 순매출 - PG - OCR - 저장 - 기타 직접비

완전원가 공헌이익
= 현금 공헌이익 - (사람 작업시간 × 30,000원/시간)
```

30,000원/시간은 시장 사실이 아닌 초기 내부 회계 가설이다. 작업시간은 `sales`, `setup`, `receipt_review`, `settlement_review`, `support`, `incident`로 나눈다. 실제 세무 지위가 확정되기 전에는 부가세를 0원으로 임의 처리하지 않고 보수적으로 분리 적립한다.

가격 셀별 허용 사람시간은 `(순매출 - 비인건 직접비) ÷ 30,000원/시간`으로 케이스마다 계산한다. 예상 시간이 허용치의 80%를 넘으면 조기 경고, 100%를 넘으면 해당 케이스의 완전원가 공헌이익 실패로 판정한다.

### 17.3 핵심 지표

- 적격 고객 대비 실제 결제율
- 상품·채널별 결제와 환불
- 자료 완성부터 초안·최종 정산까지의 시간
- OCR 필드별 정확도와 필드별 수정률
- 영수증 한 장당 검수시간
- 여행당 누락·환율 이견·수정·이의 수
- 총무 승인율과 참여자 열람·승인·이의율
- 미탐지 금액 오류와 잠금 취소 수
- 여행당 사람 작업시간과 공헌이익
- 소개·다음 여행 결제·반복 주최자 유료 약정
- 무단 접근·개인정보 노출·잘못 잠긴 정산 수

30일 유지율은 핵심 지표로 사용하지 않는다. 여행은 저빈도 이벤트이므로 동일 총무의 다음 여행, 소개와 반복 주최자의 다음 유료 케이스를 본다.

## 18. 테스트 전략

### 18.1 테스트 피라미드

| 계층 | 도구 | 필수 검증 |
|---|---|---|
| 순수 도메인 | Vitest + fast-check | bigint 원 금액·반올림·안정 tie-break·상태머신·정산 불변식·동일 ID 집합의 순열 불변성 |
| DB 통합 | 임시 Postgres/Supabase | 전체 마이그레이션, 트랜잭션, unique, cross-trip/org 차단 |
| API 계약 | Vitest/Supertest 계열 | 인증, scope, 만료, 웹훅 멱등, 삭제 요청 |
| MCP 회귀 | 기존 smoke 확장 | 기본 11개와 기능 플래그별 도구 계약, 공통 서비스 결과 일치 |
| 브라우저 E2E | Playwright | 결제 sandbox, 접수, OCR 검수, 승인, 공유, 폐기 |
| OCR 골든 | 비식별·합성 영수증 3주차 10건, 6주차까지 30건 이상 | 금액·통화·날짜·상점 필드별 정확도와 회귀 |
| 보안 부정경로 | 통합/E2E | 타 여행, 타 참여자, 폐기 토큰, 악성 파일, 로그 PII |

### 18.2 출시 차단 테스트

- 금액·통화 미확정 OCR이 expense로 저장되지 않음
- expense share 합계가 지출 원 단위 금액과 다르면 잠금되지 않음
- net 합계가 0이 아니면 잠금되지 않음
- 만료·폐기·타 여행 토큰으로 조회되지 않음
- participant share grant로 총무 승인·잠금 요청을 할 수 없고 organizer review grant로 참여자 승인·이의를 대신할 수 없음
- 운영자 허용 목록 밖 사용자가 실제 데이터에 접근하지 못함
- 계좌 원문이 Kakao·CSV·로그·분석 이벤트에 나타나지 않음
- 같은 PG 웹훅이 두 번 와도 결제·주문 상태가 한 번만 변함
- 위조된 웹훅이 도착해도 Toss 조회 결과의 주문번호·금액·결제키가 일치하지 않으면 상태가 변하지 않음
- 잠긴 정산의 입력을 바꾸면 새 버전이 생기고 과거 버전은 불변
- 삭제 작업 후 DB, 객체 저장소, OCR 사본, 가명 이벤트의 대상 데이터가 사라지고 백업 복구 시 tombstone이 재적용됨
- 프로덕션 필수 구성 누락 시 실제 접수·결제·잠금이 fail-closed됨

OCR 모델의 자동 인식률과 무관하게 사람 검수 후 고객에게 전달된 미탐지 금액 오류 목표는 0건이다.

## 19. CI/CD와 운영 안정성

### 19.1 CI

모든 PR에서 다음을 실행한다.

1. 타입검사
2. 린트와 포맷 검사
3. 기존 로직 테스트와 신규 도메인 테스트
4. DB 마이그레이션·통합 테스트
5. MCP 스모크
6. 핵심 Playwright E2E
7. 의존성·비밀값·로그 PII 검사

1주차에 모든 미래 E2E를 한꺼번에 만들지는 않는다. CI 골격과 기존 회귀·인증·실데이터 격리 테스트를 먼저 배포하고, 각 주차의 수직 슬라이스가 추가될 때 해당 DB·API·E2E·보안 테스트를 같은 PR의 출시 조건으로 붙인다.

### 19.2 배포

- 모든 PR은 Vercel Preview와 합성 데이터 DB에서 검증한다.
- 프로덕션 마이그레이션은 expand/contract 방식만 사용한다.
- 애플리케이션은 이전·신규 스키마를 함께 읽을 수 있는 기간을 둔다.
- DB 변경을 같은 배포에서 파괴적으로 되돌리지 않는다. 앱 롤백과 후속 정합성 마이그레이션을 사용한다.
- 첫 유료 여행 전 실제 백업을 별도 임시 DB에 복구하는 리허설을 완료한다.
- 배포 후 health, 인증, 토큰 폐기, 정산 샘플과 삭제 작업을 스모크한다.

### 19.3 기능 플래그

- `REAL_DATA_INTAKE_ENABLED`
- `BETA_LEAD_INTAKE_ENABLED`
- `MCP_DEMO_ENABLED`
- `DEMO_SURFACES_ENABLED`
- `PAYMENTS_ENABLED`
- `RECEIPT_UPLOAD_ENABLED`
- `PAYOUT_METHODS_ENABLED`
- `SETTLEMENT_FINALIZATION_ENABLED`
- `ORGANIZATIONS_ENABLED`

필수 보안·법률·공급자 구성 하나라도 빠지면 관련 플래그는 자동으로 꺼진다.

프로덕션 기본값은 모든 플래그 `false`다. `PAYOUT_METHODS_ENABLED`와 `ORGANIZATIONS_ENABLED`는 각각 별도 후속 spec이 승인되기 전에는 켤 수 없다.

## 20. 12주 실행 로드맵

### 20.1 용량 가정

- 창업자 집중시간 주 30~35시간
- 개발·테스트 60%
- 고객 모집·콘시어지 운영 20%
- 개인정보·PG·공급자·운영문서 10%
- 장애·학습·버퍼 10%
- 한 주에 프로덕션 주요 수직 슬라이스 하나만 완료한다.
- 동시에 운영하는 유료 여행은 최대 3건으로 제한한다.
- 개발·테스트 가능시간은 주 약 18~21시간이므로 각 슬라이스는 필수 경로 하나와 그 출시 차단 테스트로 제한한다. 계획된 슬라이스가 끝나지 않으면 다음 주 기능을 당겨 만들지 않는다.
- 계좌 저장, 자동 알림, 조직·청구, outbox와 범용 MCP 실데이터 지원은 해당 게이트 전 용량 계산에서 제외한다.

### 20.2 주차별 결과

| 주차 | 개발·운영 결과 | 주간 종료 조건 |
|---|---|---|
| 1 | CI 골격, 운영자 인증, 레거시 경로 실데이터 격리, 접근로그, 기본 약관·개인정보·국외처리 고지, 위험 기능 비활성화, 데이터·자금 흐름도, 백업·복구 | 첫 실데이터 안전 게이트 통과 |
| 2 | 주문·결제·환불과 케이스 상태, 주문 연결 동의 버전, 환불 문구, 작업시간 계측, 가격 셀 제안 | 첫 적격 고객 10명 제안·결제 결과 확보 |
| 3 | private 업로드, OCR 실행·검수·삭제, 환율 출처 | 실제 영수증이 승인 없이는 원장에 반영되지 않음 |
| 4 | 정산 스냅샷, 총무 승인, 참여자 검토창·이의, 만료 공유 | 유료 여행 3건 정확히 마감 |
| 5 | 주문·OCR·정산·시간을 잇는 운영자 워크벤치 | 수작업 병목 상위 항목 식별 |
| 6 | 5~10건 전달, 가격·SLA·공헌이익 분석 | B 지속·수정·중단 결정 |
| 7 | 반복 주최자 10명 문제·구매자·반복성 인터뷰 | 공통 반복 워크플로 도출 |
| 8 | 반복 주최자 두 오퍼 제안과 실제 유료 파일럿 결제 | C Go/No-Go 결정 |
| 9 | 조건부 C 브레인스토밍·하위 spec·사용자 승인 | 실제 유료 워크플로에 맞는 범위 고정 |
| 10 | 승인된 경우에만 조직·멤버십·테넌트 격리 | cross-org 접근 테스트 통과 |
| 11 | 승인된 경우에만 템플릿·최소 주최자 포털 | 민감정보 없이 새 여행 생성·초대 |
| 12 | 반복 결제·계약, 운영시간 비교, 보안·복구 검토 | 반복성·마진·안전 최종 결정 |

모든 주차는 앞 게이트를 통과한 뒤 시작하는 활성 실행 주차다. 표본·외부 심사로 게이트가 연장되면 뒤 주차도 같은 만큼 이동하며, 달력상 날짜만으로 다음 단계에 진입하지 않는다.

8주차 C 게이트를 통과하지 못하면 9~12주에는 조직 코드를 만들지 않는다. 해당 기간은 B 오퍼·ICP·운영 병목 개선 또는 명시적 중단에 사용한다. 게이트를 통과하더라도 9주차 첫 결과는 코드가 아니라 별도 C 하위 spec의 사용자 승인이다.

## 21. Go / Iterate / Stop 게이트

모든 수치는 시장 사실이 아니라 승인된 실험 기준이다. 게이트는 순차적이며, 결과가 Go·Iterate·Extend·Stop 중 하나로 기록되기 전에는 다음 게이트를 시작하지 않는다. `Extend`는 안전사고가 없고 표본만 부족할 때 각 게이트마다 최대 2개 활성 주차, 1회만 허용한다.

### 21.1 1주차: 첫 실데이터 안전 게이트

Go:

- 운영자 인증·접근기록·feature flag가 fail-closed함
- 약관·개인정보·국외처리·삭제 절차가 실제 화면에 연결됨
- 백업·복구, cross-trip 차단과 레거시 MCP·Web·Prototype의 실데이터 거부 테스트 통과
- 계좌 원문과 Toss 딥링크가 비활성화됨
- 참여자 데이터 처리 근거·고지에 대한 전문 검토와 공급자 국외처리 게이트 완료

Stop:

- 하나라도 미달하면 실제 연락처·계좌·영수증을 받지 않는다.
- 결함은 합성 데이터로 수정할 수 있지만 안전 게이트 자체에는 Extend를 적용하지 않는다.

참여자 만료·폐기 토큰 테스트는 공유 기능을 켜는 4주차 기능별 안전 게이트다. 1주차에 아직 없는 공유 기능을 통과 조건으로 요구하지 않는다.

### 21.2 2주차: 지불의사 게이트

Go:

- 동일 오퍼를 받은 적격 고객 10명 중 3명 이상이 명시 가격으로 실제 결제한다.

Iterate:

- 첫 10명에서 1~2명 결제하면 이탈 사유와 구매 이유를 바탕으로 오퍼 또는 가격을 한 번만 수정하고 새 적격 고객 10명에게 다시 제안한다.
- 첫 10명에서 0명이 결제해도 두 번째 통제된 오퍼를 한 번만 시험한다. 인터뷰 의향은 결제로 대체하지 않는다.

Stop/Pivot:

- 수정 오퍼의 새 적격 고객 10명에서도 3명 미만이면 B 개발 확장을 멈추고 ICP·오퍼를 재설계한다.
- 특히 두 오퍼로 적격 고객 총 20명에게 제안해 결제가 0건이면 해당 ICP·오퍼는 즉시 중단한다.

### 21.3 4주차: 신뢰 전달 게이트

Go:

- 유료 여행 3건 최종 마감
- 모든 정산 불변식과 총무 승인이 충족
- 오류·이견·수정·작업시간 100% 기록
- 사람 검수 후 고객에게 전달된 미탐지 금액 오류 0건

Safety Stop:

- 잘못 잠긴 정산, 무단 접근 또는 개인정보 노출이 1건이라도 발생하면 신규 접수를 중단한다.

Extend/Stop:

- 안전사고 없이 1~2건만 완료됐다면 최대 2개 활성 주차 안에 3건까지 채운다. 그 뒤에도 3건을 완료하지 못하면 전달 워크플로를 축소하거나 B를 중단한다.
- 결제는 됐지만 0건 완료라면 추가 자동화보다 자료 수집·운영 실패를 먼저 분석하고 신규 접수를 중단한다.

### 21.4 6주차: 콘시어지 경제성 게이트

초기 게이트 표본은 결제 시각 순으로 처음 완료된 5건부터 최대 10건이다. 11건 이상이 완료돼도 처음 10건으로 판정해 유리한 케이스를 고르지 않는다. 가격 셀의 마진 통과에는 같은 가격으로 완료된 케이스가 최소 3건 필요하며, 그 셀의 완전원가 공헌이익 합계와 중앙값이 모두 0원 이상이어야 한다.

Go:

- 판정 표본 5~10건 완료
- SLA 내 마감률 80% 이상
- 위 최소 표본을 충족한 한 가격 셀에서 완전원가 공헌이익 합계·중앙값 0원 이상
- 재사용 또는 유료 소개 의사를 보인 총무 2명 이상

Iterate:

- 초기 표본에서 SLA·마진·재사용 조건 중 정확히 하나만 미달이면 사람 시간이 가장 큰 작업 또는 오퍼 한 항목만 한 번 바꾼다. 변경 배포 뒤 결제된 신규 완료 5~10건을 별도 재측정 코호트로 고정하고 최대 2개 활성 주차 안에 모든 Go 조건을 다시 측정한다. 초기 표본과 합산하지 않는다.
- 기한 안에 재측정 코호트 5건을 채우지 못하거나, 5~10건에서 하나라도 미달이면 B는 Go가 아니며 추가 자동화와 C 탐색을 중단하고 ICP·가격·서비스 범위를 다시 설계한다. 이 게이트에서 두 번째 수정은 허용하지 않는다.

Extend:

- 안전·정확성 문제가 없고 일정 때문에 3~4건만 완료했다면 최대 2개 활성 주차 안에 최소 5건을 채운다.
- 연장 후에도 5건 미만이면 B를 Go로 판정하지 않고 신규 기능 개발을 멈춘 채 획득·전달 방식의 축소 또는 중단을 결정한다.

Stop/Pivot:

- 표본을 채운 뒤 SLA·마진·재사용 조건이 둘 이상 동시에 미달하면 C 탐색으로 넘어가지 않고 B 오퍼를 재설계한다.
- 안전·정확성은 충족해도 어떤 가격 셀도 3건을 채우지 못하면 마진 게이트 미충족으로 처리한다.

### 21.5 8주차: B→C 전환 게이트

Go:

- 반복 주최자 10명 이상 조사
- 서로 다른 반복 주최자 고객 2명 이상이 2회 이상 여행을 전제로 실제 유료 파일럿을 결제
- 조사 종료 시점의 모든 유료 고객에서 필수 워크플로 유사도 70% 이상

반복 주최자 고객은 결제 의사결정권을 가진 고유 개인 또는 조직 하나를 한 단위로 센다. 같은 조직의 참가자 여러 명을 여러 고객으로 세지 않는다. 워크플로 유사도는 조사 종료 시점의 모든 유료 고객이 각각 `필수`로 표시한 단계 집합의 전체 합집합을 분모, 전체 교집합을 분자로 한 비가중 다자간 Jaccard 비율이며 선택·브랜딩 단계는 제외한다. 유리한 두 고객만 골라 계산하지 않는다.

Iterate:

- 첫 10명에서 한 명만 결제하거나 2명 이상 결제했어도 공통 흐름이 70% 미만이면 최대 5명을 추가 조사하고 조직 코드를 만들지 않는다.
- 환불 가능한 보증금·구두 약정은 유료 파일럿 결제로 세지 않고 후속 접촉 우선순위로만 사용한다.

Stop C:

- 첫 10명에서 결제 0건이면 두 번째 오퍼로 최대 15명까지 조사한다. 적격 반복 주최자 총 15명, 두 오퍼 후 실제 유료 파일럿 결제가 0이면 B2B2C 제품화를 중단한다.
- 15명까지 조사해도 결제 고객이 한 명뿐이면 C는 Go가 아니며 B를 계속할지 별도로 판단한다.
- 15명까지 조사해 유료 고객이 2명 이상이어도 모든 유료 고객의 필수 워크플로 유사도가 70% 미만이면 공통 제품 근거가 없으므로 C 제품화를 중단한다.

### 21.6 12주차: 반복 제품 게이트

반복 케이스는 같은 고객의 첫 유료 완료 케이스 뒤에 결제·완료된 다음 여행이다. 확정 계약이나 선결제만 있고 두 번째 여행이 완료되지 않은 고객은 완료 표본으로 세지 않는다. 운영시간 감소는 고객별 첫 케이스 대비 두 번째 케이스의 `총 사람 작업분 ÷ max(지출 건수, 1)` 감소율로 짝지어 계산하고 참여자 수 차이도 함께 보고한다. 마진은 서로 다른 고객의 반복 완료 케이스 최소 2건에서 합계와 중앙값을 모두 본다.

Go:

- 반복 주최자 고객 2명 이상이 두 번째 여행을 결제·완료
- 위 짝지은 고객별 운영시간 감소율의 중앙값 30% 이상이며 어느 반복 케이스도 첫 케이스보다 10% 넘게 악화되지 않음
- 두 고객 이상의 반복 완료 케이스에서 완전원가 공헌이익 합계·중앙값 0원 이상
- 심각한 정산·보안 사고 0건

Extend:

- 안전사고 없이 반복 완료 고객이 한 명이면 새 기능을 추가하지 않고 최대 2개 활성 주차 안에 두 번째 고객의 반복 여행 완료를 기다린다. 연장 뒤에도 한 명이면 C 확장 Go가 아니며 B 서비스 또는 제한 파일럿으로 되돌린다.

Iterate:

- 반복 완료 고객이 2명 이상이고 시간·마진 조건 중 정확히 하나만 미달이면 운영 병목 하나만 한 번 수정한다. 최대 2개 활성 주차 안에 수정 후 반복 완료 케이스 2건 이상을 추가로 측정해 모든 Go 조건을 다시 평가하고, 하나라도 미달하면 C 확장을 중단한다.

Stop C:

- 반복 완료 고객이 0명이거나, 시간·마진 조건이 둘 다 미달하거나, 고객별 요구가 달라 맞춤 용역이 되면 B2B2C SaaS 확장을 중단한다.
- 심각한 정산·보안 사고가 한 건이라도 발생하면 표본과 무관하게 Safety Stop을 적용한다.

## 22. 하위 명세와 구현 계획 분해

이 문서는 상위 사업화 charter다. 사용자가 이 작성본을 명시적으로 승인해도 곧바로 5개 구현 계획을 일괄 작성하지 않는다. 아래 각 독립 영역마다 `하위 spec 작성 → 사용자 명시 승인 → 해당 영역에 writing-plans 적용` 순서를 지킨다. 앞 영역의 구현·실측 결과가 다음 영역의 가정을 바꾸면 다음 하위 spec에서 반영한다.

| 순서 | 하위 명세 영역 | 독립 완료 결과 | 의존성 |
|---|---|---|---|
| 00 | 신뢰 기반 | CI, staff auth, 실데이터/레거시 격리, 개인정보·feature flag, 백업·복구 | 없음 |
| 01 | 주문·결제·케이스 | 리드부터 결제·환불·상태·작업시간까지 한 폐쇄 루프 | 00 |
| 02 | 금액·환율·영수증 증빙 | bigint/decimal 금액 기반, 출처 환율, private 업로드부터 사람 승인 expense까지 | 00, 01 |
| 03 | 정산 잠금·공유 | snapshot, 승인·검토창·이의, 만료 공유 | 00~02 |
| 04 | 운영·측정·유료 베타 | 워크벤치, 공헌이익, 5~10건 운영·게이트 | 01~03 |

상위 작성본 승인 다음 단계는 `00 신뢰 기반` 하위 spec 작성과 사용자 검토다. 00의 하위 spec이 승인되기 전에는 00 구현 계획이나 코드를 만들지 않는다. 01~04도 같은 게이트를 각각 통과한다.

조건부 B2B2C는 현재 구현 계획 05로 미리 고정하지 않는다. 8주차 게이트를 통과한 뒤 실제 모든 유료 고객의 공통 흐름으로 별도 브레인스토밍 → 하위 spec → 사용자 승인 → 구현 계획 순서를 다시 거친다.

## 23. 공통 Definition of Done

각 구현 작업은 다음을 모두 만족해야 완료다.

1. 승인된 spec 요구사항과 추적되는 작업 ID가 있다.
2. 실패하는 테스트를 먼저 작성하고 실패 원인을 확인했다.
3. 최소 구현으로 테스트를 통과했다.
4. 타입·단위·통합·배포 구성별 MCP·해당 수직 슬라이스의 필수 E2E가 통과했다.
5. 인증·권한·민감정보·로그·보유기간 영향을 검토했다.
6. 마이그레이션은 expand/contract이며 이전 코드와 호환된다.
7. 관측 이벤트에 분모와 오류 원인이 있고 PII가 없다.
8. 운영자 문구·오류 메시지·런북을 갱신했다.
9. Vercel Preview에서 합성 데이터로 창업자가 확인했다.
10. Claude의 비식별 독립 검토 또는 동등한 2차 검토를 반영했다.
11. 롤백·feature flag·데이터 정합성 확인 절차가 있다.
12. 한국어 PR에 변경 이유, 사용자 영향, 검증 결과가 기록됐다.

## 25. 승인 기록

대화형 설계에서 다음이 승인되었다.

1. 제품·사업·콘시어지 운영 구조
2. 모듈형 모놀리스, 인증·권한, 정산 스냅샷, OCR·개인정보 기술 구조
3. 테스트 전략, 12주 일정, Go/Iterate/Stop과 Codex + Claude 역할 분담

사용자가 이 상위 작성본을 명시적으로 승인한 후 `00 신뢰 기반` 하위 spec부터 작성한다. B 단계 00~04는 각 하위 spec을 사용자가 승인한 뒤에만 해당 구현 계획을 작성하며, 구현은 그 계획에 대한 별도 실행 승인 후 시작한다. 조건부 C는 8주차 증거 이후 별도 설계 승인을 받는다.
