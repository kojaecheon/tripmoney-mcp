# TripMoney 제품 표면 UX 리디자인 설계

- 작성일: 2026-09-06
- 상태: 대화형 설계 4개 부분(정보 구조, 디자인 시스템, 화면 레이아웃, 목업 구현·검증) 승인 완료, 참고 디자인(Clay·Discord 분석) 반영 개정본을 2026-09-06 사용자가 승인함. 다음 단계는 목업 구현 계획
- 참고 디자인: 사용자가 제공한 Clay 디자인 분석과 Discord 디자인 분석. 채택·제외 근거는 4.8절에 기록한다.
- 상위 명세: [사업화 설계](2026-08-26-tripmoney-commercialization-design.md) 16장 사용자 표면
- 관련 명세: [00 신뢰 기반 하위 설계](2026-09-02-tripmoney-trust-foundation-design.md) 3.2 경로 계약
- 기준 코드: `ea22363`의 `public/index.html`, `public/app.html`, `lib/prototypeStore.ts` 합성 데이터
- 산출물 경계: 이 설계 문서와 `docs/design/` 아래의 정적 목업. `public/`, `vercel.json`, `lib/`, `api/`, DB, 배포 설정은 변경하지 않는다.
- 승인 경계: 작성본 승인 → `writing-plans` 목업 구현 계획 → 목업 작성. 이 문서는 프로덕션 화면 구현의 승인이 아니며, 프로덕션 구현은 01~04 하위 명세의 각 게이트를 따른다.

## 1. 목적과 완료 결과

현재 웹 표면은 유료 베타 신청 랜딩과 운영자 데모 콘솔 두 화면이며, 사업화 설계 16장이 정의한 네 표면 중 총무 검토와 참여자 공유는 존재하지 않고 운영자 워크벤치는 데모 콘솔 수준이다. 이 설계는 네 표면을 "실제 사용성 있는 플랫폼"으로 보이고 동작하게 하는 UX와 디자인 시스템을 정의하고, 백엔드 구현보다 먼저 검증할 수 있는 클릭 가능한 목업을 만든다.

완료 결과는 두 가지다.

| 산출물 | 위치 | 용도 |
|---|---|---|
| 설계 문서 | 이 파일 | 01~04 하위 명세와 구현 계획이 참조하는 UX 기준 |
| 클릭 가능한 목업 | `docs/design/mockups/` | 고객 제안·인터뷰용 시연, 구현 시 화면 기준, 문구·흐름 검토 |

### 1.1 승인된 결정

- 리디자인 대상은 사업화 설계 16장의 네 표면(공개 랜딩, 운영자 워크벤치, 총무 검토, 참여자 공유)이다. 총무가 직접 쓰는 셀프서비스 앱이나 채팅 결과 화면 중심 구조는 채택하지 않는다.
- 산출물은 설계 문서와 합성 데이터로 움직이는 정적 HTML 목업이다. 프로덕션 경로에 연결하지 않으며 00 게이트와 충돌하지 않는다.
- 디자인 방향은 기존 여행 서류 모티프(보딩패스, 스탬프)를 네 표면 전체의 시스템으로 확장하는 것이다.
- 확장 방식은 접근 C다. 여정 레일을 뼈대로 삼고 서류 컴포넌트는 보딩패스, 스탬프, 수하물 태그 세 종류로 제한한다.
- 참여자 공유와 총무 검토는 모바일 우선, 운영자 워크벤치는 데스크톱 우선, 랜딩은 양쪽 대응이다.
- 다크 모드는 범위에서 제외한다.
- 목업은 `docs/design/` 아래에 두고 빌드 도구와 프레임워크 없이 만든다.
- 참고 디자인 반영 범위는 추천안이다. Clay 분석을 주 참고로 삼고 Discord 분석에서는 페이지 리듬과 버튼 위계 원칙만 채택한다. 어두운 캔버스, 그라데이션, 굵은 대문자 제목, 40px 이상 모서리는 채택하지 않는다.

### 1.2 비목표

- 실제 API 연동, 인증, 결제, 파일 업로드는 목업에 넣지 않는다.
- `/checkout`, `/intake` 화면은 01 영역이므로 이 설계에서 정의하지 않는다.
- 기존 `public/index.html`, `public/app.html`의 수정과 교체는 하지 않는다. 교체 시점은 01~04 구현 계획에서 정한다.
- 참여자 고지 문구, 약관, 개인정보 문구의 법률적 확정은 하지 않는다. 목업에는 "검토 전 문구" 표시를 붙인 자리 표시 문구만 넣는다.
- 카카오 공유 실제 템플릿 등록, Toss 딥링크, 계좌 표시는 넣지 않는다.

## 2. 확인된 현재 기준선

2026-09-06에 `ea22363` 기준으로 확인한 사실이다.

- `public/index.html`은 히어로, 절차 4단계, 오퍼, 신청 폼, 대상 고객, 마무리의 여섯 구획으로 된 랜딩이며 종이·잉크 팔레트(`--paper #F5EFE3`, `--ink #172133`), Fraunces 제목 서체, Space Grotesk 본문, Pretendard 한글 서체를 쓴다. 히어로에 채팅 화면과 보딩패스 카드가 있다.
- `public/app.html`은 왼쪽 여행 목록과 오른쪽 정산·비용·개요 탭으로 된 운영자 데모 콘솔이다. 같은 팔레트 계열이지만 제목 서체가 Space Grotesk이고 숫자 서체가 Space Mono여서 랜딩과 토큰이 다르다. 정산 탭의 송금 제안이 보딩패스 컴포넌트로 표시된다.
- 랜딩의 신청 폼은 이름, 연락처, 여행명, 목적지, 가격 의향 등을 받는다. 00 신뢰 기반 7.1은 연락 수단 1개, 동의 여부, 정책 버전만 받도록 계약을 바꿨다.
- 00 신뢰 기반 3.2는 Production에서 `/prototype`을 404로 닫고 `/operator`는 00B 이후 직원 인증 뒤에만 열며 review와 share 경로는 00에서 구현하지 않는다고 정했다.
- 합성 데이터는 `lib/prototypeStore.ts`에 "방콕" 여행, 멤버, 일정, 지출이 있다. 목업은 이 구성을 참고하되 자체 `data.js`로 독립한다.
- 정산 순수 함수 `lib/settlement.ts`와 내보내기 `lib/settlementExport.ts`의 출력 형식(멤버별 paid·owed·net, 송금 제안, 카톡 문구, CSV, 카드)은 화면 내용의 기준이 된다.

## 3. 정보 구조

### 3.1 여정 레일과 케이스 상태 대응

여정 레일은 사업화 설계 5.2의 케이스 상태 여섯 개를 비행 단계에 1:1로 대응시킨 공통 컴포넌트다. 네 표면이 같은 레일을 쓴다.

| 순서 | 단계명 | 케이스 상태 | 단계 종료 조건(5.3 체크포인트) |
|---|---|---|---|
| 1 | 체크인 | `collecting` | 멤버·결제자·통화·분담·원본 목록이 모두 확인됨 |
| 2 | 검수 | `reviewing` | 모든 지출의 금액·통화가 확정되고 정산 초안 불변식이 통과함 |
| 3 | 탑승 승인 | `awaiting_organizer` | 총무가 해당 버전을 승인함 |
| 4 | 순항 검토 | `participant_review` | 검토창이 종료되고 미해결 금액 이의가 0건임 |
| 5 | 착륙 잠금 | `finalized` | 총무 잠금 요청과 내부 QA 승인으로 스냅샷이 잠김 |
| 6 | 도착 | `delivered`, `closed` | 정산 결과가 전달되고 삭제 예정일이 기록됨 |

보조 상태 `paused`, `cancelled`, `reopened`는 레일 오른쪽 끝의 배지 하나로 표시하고 단계를 늘리지 않는다. 재개된 케이스는 새 정산 버전 번호와 함께 배지를 표시한다. SLA 시계는 결제와 필수 자료 체크리스트가 모두 완료된 시점에 시작하므로, 레일에서는 "검수" 단계 진입점에 "SLA 시작" 표시를 붙인다.

### 3.2 표면별 내용

#### 공개 랜딩 `/`

- 헤드라인은 "근거가 남는 해외여행 최종 정산"을 중심으로 하고, "여행 총무 AI"는 부제 이하로 내린다.
- 히어로 오른쪽에는 완성된 정산 결과 하나를 서류 컴포넌트 3종(보딩패스, 수하물 태그, 총무 승인 스탬프)으로 보여준다. 현재의 채팅 화면 목업은 제거한다.
- 히어로 아래 특징 카드 다섯 개는 표현색을 순환하며 각 카드 안에 실제 UI 조각(수하물 태그가 붙은 지출 행, 환율 근거 표, 보딩패스, 참여자 스탬프, 운영자 SLA 큐)을 넣는다.
- 절차 구획은 종이색 전폭 밴드 위에 여정 레일 하나로 여섯 단계를 설명하고 각 단계의 종료 조건을 짧게 적는다.
- 가격 셀은 검수형 29,000원과 마감 대행형 59,000원 두 개를 나란히 두고 범위(인원·건수), 초안 SLA, 수정 묶음 횟수, 참여자 지원, 환불 조건을 같은 항목 순서로 적는다. 가격은 고객이 실제 결제할 최종 금액으로 표시한다.
- 적격 조건과 제외 조건을 각각 목록으로 표시한다. "3~8명"은 운영 범위로만 표기하고 시장 통계처럼 쓰지 않는다.
- 고객 자금을 보관하지 않는다는 점, 참여자 연락처를 받지 않고 총무가 링크를 직접 전달한다는 점을 고지 구획에 적는다.
- 신청 폼은 연락 수단 1개(이메일 또는 전화번호), 기본 해제된 동의 체크, 정책 버전 표시만 둔다. 접수 비활성 변형에서는 폼 자리에 접수 중단 안내와 정책 링크만 남긴다.
- 신청 뒤에는 크림색 마무리 CTA 밴드를 두고, 푸터는 크림색으로 큰 워드마크와 약관, 개인정보, 국외처리 고지 링크 자리를 둔다. 어두운 푸터는 쓰지 않는다.

#### 총무 검토 `/review/:grant`

- 상단 고정 헤더에 여행명, 정산 버전 번호, 여정 레일, 현재 단계명을 둔다.
- 결과 구획: 총액, 멤버별 paid·owed·net 표, 송금 제안을 보딩패스 목록으로 표시한다.
- 근거 구획: 지출 목록의 각 행에 수하물 태그로 영수증 근거 상태를 표시하고, 환율 출처·시각·수동 사유를 별도 목록으로 표시한다.
- 잠금 조건 구획: 본인 승인, 검토창 종료, 미해결 이의 0건의 세 조건을 충족 여부와 함께 표시한다. 정산에서 제외된 지출이 있으면 근거 구획 끝에 "정산 제외 항목"으로 건수와 금액을 적는다.
- 수정 이력 구획: 버전별 변경 요약과 남은 수정 묶음 횟수(검수형 1회, 마감 대행형 2회)를 표시하고 수정 요청 제출 양식을 둔다.
- 승인 행위: "이 버전 승인" 버튼을 누르면 총무 승인 스탬프가 찍히고 승인 시각이 기록된다. 이미 승인한 버전에는 버튼 대신 스탬프만 남는다.
- 참여자 현황: 승인, 이의, 무응답 건수를 집계로 표시하고 검토창 마감 시각을 적는다.
- 최종 잠금 요청: 본인 승인 완료, 검토창 종료, 미해결 이의 0건의 세 조건이 모두 충족될 때만 활성화하며, 충족 전에는 비활성 사유를 버튼 아래에 적는다.
- 공유 행위: 참여자 링크 복사와 카카오 공유 미리보기를 제공한다. 미리보기에는 여행명, 정산 버전, 기준 환율, 송금 제안만 들어간다.

#### 참여자 공유 `/share/:token`

- 첫 화면은 전면 고지 화면이다. 운영자, 목적, 항목, 보유기간, 국외처리, 권리 행사 방법을 적고 "계속", "삭제 요청", "이의 경로"의 세 선택지를 둔다. 문구에는 "검토 전 문구" 표시를 붙인다.
- 본문 헤더에 여행명, 정산 버전, 여정 레일을 두되 총무 화면보다 작게 표시한다.
- 본인 구획: 참여자 별칭과 본인의 paid·owed·net만 표시한다.
- 송금 구획: 본인이 보내거나 받는 송금만 보딩패스로 표시하고 스텁에는 상대 별칭과 금액, "이름·금액 복사" 버튼만 둔다. 계좌번호는 표시하지 않는다.
- 근거 구획: 환율 기준, 반올림 방식, 영수증 원본 존재 여부, 마지막 수정 시각, 검토창 마감까지 남은 일수를 표시한다. 다른 참여자의 계좌와 영수증 원본은 표시하지 않는다.
- 결정 행위: 승인, 이의 제기(사유 입력), 이의 철회를 제공하고 결과를 참여자 스탬프로 표시한다. 무응답은 승인이 아니므로 별도 상태 문구를 둔다.
- 만료·폐기 화면: 링크가 만료되거나 폐기된 경우 여행명 없이 상태와 총무에게 문의하라는 안내만 표시한다.

#### 운영자 워크벤치 `/operator`

- 로그인 화면은 이메일 매직링크 입력 하나와 안내 문구로 구성한다.
- 상단 내비게이션은 케이스 큐, 리드, 설정의 세 항목과 로그인한 직원 표시, 로그아웃이다. 리드 탭은 00B의 마스킹된 리드 목록과 QA 의견 기능을 담는다.
- 케이스 큐: 왼쪽 열에 케이스 번호, 상품 종류, 현재 단계, SLA 잔여 시간 또는 일시정지 사유, 다음 조치를 표시하고 SLA 잔여 시간 순으로 정렬한다.
- 케이스 상세 상단: 여정 레일과 5.3 체크포인트 체크리스트, 현재 차단 조건을 표시한다.
- 자료수집 체크리스트: 멤버, 결제자, 통화, 분담, 원본 목록 항목의 확인 상태를 표시한다.
- 영수증 검수: 원본, OCR 추출값, 수정값·승인의 3열 비교로 표시하고 검수자와 승인 시각을 적는다.
- 환율: 통화쌍별 출처, 시각, 수동 사유를 표시한다.
- 정산 버전 패널: 버전 목록과 11.3 불변식 8개 항목의 통과·실패를 표시한다.
- 이의 목록: 참여자별 이의 사유, 상태, 해결 기록을 표시한다.
- 내부 QA 승인과 잠금: QA 의견 입력, QA 승인 스탬프, 잠금 실행 버튼을 두며 잠금 버튼은 불변식 전부 통과와 총무 잠금 요청이 있을 때만 활성화한다.
- 카카오 미리보기와 링크 폐기, 작업시간·비용·환불, 보유기간·삭제 요청·사고중단 스위치를 하단 한 줄의 세 패널로 둔다.

### 4.2 여정 레일 컴포넌트

- 가로 점선 위에 원 여섯 개를 두고, 지난 단계는 잉크색으로 채운 원, 현재 단계는 파란 테두리와 단계명, 남은 단계는 빈 원으로 표시한다.
- 데스크톱에서는 여섯 단계명이 모두 보이고, 모바일에서는 현재 단계와 앞뒤 한 단계씩만 보이며 옆으로 스크롤할 수 있다.
- 각 단계를 누르거나 마우스를 올리면 3.1의 단계 종료 조건이 말풍선으로 나타난다.
- 보조 상태 배지는 레일 오른쪽 끝에 하나만 표시하고 문구는 "일시정지 · 고객 답변 대기", "취소됨", "재개 · v3" 형식이다.
- "검수" 단계 진입점에 "SLA 시작"이라는 작은 표시를 둔다.

### 4.3 서류 컴포넌트 3종

보딩패스는 송금 한 건에 한 장이다.

- 왼쪽 본체에 "보내는 사람 → 받는 사람"과 송금 순번, 오른쪽 스텁에 금액과 행위 버튼을 둔다. 본체와 스텁 사이는 절취선이다.

### 4.4 모티프 예산 규칙

1. 모티프는 상태와 관계만 전달한다. 금액은 항상 표 형식 숫자와 글자 라벨로도 함께 적는다.
2. 한 화면에 서류 컴포넌트 종류는 세 가지를 넘기지 않는다. 같은 종류의 반복(보딩패스 목록)은 허용한다.
3. 폼, 필터, 설정, 로그인에는 모티프를 쓰지 않는다. 표에는 지출 목록의 근거 태그(수하물 태그)만 허용한다.
4. 스탬프는 4.3의 여섯 종류 외에 추가하지 않는다.
5. 새 은유가 필요하면 이 문서를 개정한 뒤에 추가한다.
6. 표현색은 랜딩과 허브의 특징 카드에만 쓴다. 검토·공유·운영자 화면에서 색은 상태만 뜻한다.
7. 채운 버튼은 앱 화면에서는 페이지에 하나, 랜딩에서는 구획(히어로, 가격, 마무리 CTA)마다 하나만 둔다. 나머지 행위는 보조 버튼이다.

### 4.5 상태 어휘와 숫자 표기

- 금액은 원화 기호 뒤에 천 단위 구분 정수를 쓰고 숫자 서체와 표 형식 숫자를 적용한다. 외화는 금액 뒤에 통화 코드를 적고 환산 원화를 괄호 없이 다음 줄에 적는다.
- 정산 버전은 "v2"처럼 표기하고 케이스 번호는 "C-014" 형식이다.
- 시각은 "2026-09-06 14:30" 형식이며 시간대 표시가 필요한 화면(운영자)에는 "KST"를 붙인다.
- 참여자 결정 상태 어휘는 승인, 이의, 철회, 무응답 네 가지다.
- 운영자 화면의 검수 차단 사유 어휘는 5.3 체크포인트의 차단 조건 문구를 그대로 쓰고, 총무 화면의 잠금 조건 어휘는 본인 승인, 검토창 종료, 미해결 이의의 세 가지로 고정한다.

### 4.6 접근성과 반응형

- 본문 대비 AA 이상, 터치 대상 44px 이상, 포커스 링은 호박색 3px 실선으로 통일한다.
- 스탬프와 수하물 태그에는 같은 문구의 텍스트 대체를 둔다.
- 기준 폭은 375, 768, 1180px 세 곳이다. 모바일에서는 한 열, 768px 이상에서 두 열, 1180px 이상에서 운영자 화면의 두 칸 구조를 적용한다. 랜딩의 콘텐츠 최대 폭은 1280px, 운영자 화면은 1180px이다.
- 모든 상호작용은 키보드로 도달할 수 있어야 하며 모달은 포커스를 가둔다.

### 4.7 문구 원칙

- 랜딩 헤드라인은 "근거가 남는 해외여행 최종 정산"을 중심으로 한다.
- 가격은 고객이 실제 결제할 최종 금액으로 표시하고 범위·SLA·환불 조건을 같은 항목 순서로 적는다.
- "3~8명"은 운영 범위로 표기한다.
- 참여자 고지, 약관, 개인정보 문구에는 "검토 전 문구" 표시를 붙여 법률 검토 전임을 드러낸다.
- 버튼은 동사로 시작하는 한국어 문장체이며 마침표를 붙이지 않는다.
- 오류와 차단 사유는 무엇이 막혔는지와 다음 행동을 한 문장씩 적는다.

## 5. 화면 설계

### 5.1 공개 랜딩

구획 순서는 헤더, 히어로, 특징 카드, 절차 밴드, 가격, 적격·제외 조건, 고지, 신청, 마무리 CTA 밴드, 푸터다. 섹션 간격은 데스크톱 96px, 모바일 56px이며 콘텐츠 최대 폭은 1280px이다.

- 헤더: 크림 캔버스 위 64px 높이, 브랜드명, 절차·가격·신청 앵커 링크, 보조형 신청 버튼 하나. 채운 버튼은 히어로에서 처음 나온다.
- 히어로: 7:5 분할. 왼쪽에 헤드라인(56px, 모바일 34px), 부제, 세 가지 사실(돈을 보관하지 않음, 3~8명 운영 범위, 여행 종료 후 정산), 채운 "신청하기"와 보조 "절차 보기" 버튼. 오른쪽에 종이색 24px 모서리 카드 안의 완성된 정산 결과(보딩패스 한 장, 수하물 태그가 붙은 지출 한 줄, 총무 승인 스탬프). 일러스트는 넣지 않는다.
- 특징 카드: 3열(태블릿 2열, 모바일 1열), 24px 모서리, 32px 안여백. 근거(라벤더, 태그 붙은 지출 행), 환율(피치, 출처·시각 표), 정산(민트, 보딩패스), 검토(오커, 참여자 스탬프 셋), 운영(딥네이비, SLA 큐 조각)의 다섯 장이며 각 카드는 제목 20px, 설명 한 문장, UI 조각으로 구성한다.
- 절차 밴드: 종이색 전폭 밴드에 여정 레일과 단계별 종료 조건, "검수" 단계의 SLA 시작 표시.
- 가격: 두 셀을 같은 항목 순서로 나란히 둔다. 검수형은 카드색에 헤어라인, 마감 대행형은 딥네이비 채움에 흰 글자로 반전한다. 각 셀의 버튼은 마감 대행형만 채움이고 검수형은 보조형이다.
- 적격·제외 조건: 4.1절의 목록을 카드색 16px 카드 두 장에 두 열로 표시한다.
- 고지: 자금 비보관, 참여자 연락처 미수집, 보유기간, 국외처리 요약을 네 칸으로 표시한다.
- 신청: 연락 수단 1개, 동의 체크(기본 해제), 정책 버전. 입력 높이 44px, 모서리 12px. 비활성 변형은 안내 문구만.
- 마무리 CTA 밴드: 종이색, 24px 모서리, 안여백 80px(모바일 40px), 40px 제목과 채운 신청 버튼 하나.
- 푸터: 크림 캔버스, Fraunces 큰 워드마크, 약관·개인정보·국외처리 링크, 사업자 정보 자리. 어두운 푸터는 쓰지 않는다.

### 5.2 총무 검토

한 열 구조이며 읽는 순서는 결과, 근거, 잠금 조건, 수정 요청, 승인, 참여자 현황, 잠금, 공유다.

- 헤더는 스크롤 시 상단에 고정하고 여행명, 버전, 레일, 현재 단계명을 포함한다.
- 승인 버튼은 헤더 바로 아래가 아니라 근거와 잠금 조건 다음에 둔다. 총무가 결과와 근거를 읽은 뒤 행동하도록 하기 위한 배치다.
- 잠금 요청 버튼은 세 조건 충족 전에는 회색이며 아래에 "검토창 종료 후 활성화" 같은 사유를 적는다.
- `participant_review` 장면에서는 승인 스탬프가 찍혀 있고 참여자 현황에 승인 2, 이의 1, 무응답 1이 표시된다.
- `finalized` 장면에서는 잠금 스탬프가 찍혀 있고 수정 요청 양식이 사라지며 공유 행위만 남는다.

### 5.3 참여자 공유

- `notice` 장면은 다른 내용을 보여주지 않는 전면 화면이다. "계속"을 누르면 `active` 장면으로 넘어가고 고지 확인 시각을 화면 하단에 표시한다.
- `active` 장면은 헤더, 본인 구획, 송금 구획, 근거 구획, 결정 행위 순서다.
- 결정 버튼은 화면 하단에 고정하고 이의 제기는 사유 입력 모달을 연다. 결정 후에는 버튼 자리에 스탬프와 철회 링크가 표시된다.
- `expired` 장면은 상태 문구와 총무 문의 안내만 표시한다.

### 5.4 운영자 워크벤치

- 1180px 이상에서 왼쪽 큐 280px, 오른쪽 상세 나머지의 두 칸 구조다. 그 미만에서는 큐가 상단 목록으로 바뀐다.
- 큐 항목은 케이스 번호, 상품, 단계, SLA 잔여 또는 일시정지 사유, 다음 조치의 다섯 정보만 표시한다.
- 상세 상단에 레일과 체크포인트 체크리스트를 두고 차단 조건은 장미색으로 표시한다.
- 영수증 검수 3열 비교는 한 지출씩 펼쳐 보는 구조이며 목록에서는 수하물 태그로 상태만 표시한다.
- 불변식 패널은 8개 항목을 통과·실패로 표시하고 실패 항목에 원인 지출로 가는 링크를 둔다.
- 하단 세 패널(공유·폐기, 작업시간·환불, 보유·삭제·사고중단)은 접힌 상태가 기본이다.
- `login` 장면은 이메일 입력과 안내 문구, "로그인 링크 받기" 버튼만 둔다.
- 케이스 상세 목업은 C-014에만 제공하고 다른 케이스는 머리 정보와 "상세 목업 없음" 안내만 둔다.

### 5.5 공통 상태 화면

- 404와 비활성 경로는 브랜드명과 한 줄 안내, 랜딩으로 가는 링크만 표시한다.
- 로딩 상태는 회색 자리 표시로, 빈 상태는 제목과 한 줄 설명, 행위 버튼 하나로 표시한다.
- 오류 상태는 무엇이 실패했는지와 다음 행동을 한 문장씩 적는다.

### 6.1 파일 구조

```

      render-review.test.cjs
      render-share.test.cjs
      render-operator.test.cjs
      pages.test.cjs
      contrast.test.cjs
```

- `tokens.css`는 4.1 토큰, 4.2 레일, 4.3 서류 컴포넌트, 공통 카드·표·폼·버튼 스타일을 담는다.
- `data.js`는 합성 여행 데이터와 장면별 상태 객체를 담고, 각 페이지는 `state` 값을 읽어 해당 장면을 그린다.
- 페이지 간 이동은 허브와 각 페이지 상단의 작은 이동 막대로 제공한다. 이 이동 막대는 목업 전용이며 실제 화면 설계의 일부가 아니다.
- `components.js`는 여정 레일, 서류 컴포넌트 3종, 버튼과 도우미를 순수 함수로 담고, `render-*.js`는 화면별 렌더 함수를 담는다. 모든 스크립트는 브라우저 전역과 CommonJS 내보내기를 함께 제공한다.
- `tests/`는 Node 내장 테스트 러너로 토큰 값, 정산 불변식, 모티프 예산, 채운 버튼 수, 헤딩 구조, 대비 AA를 자동 검사한다. 실행 명령은 `node --test docs/design/mockups/tests/*.test.cjs`이다.
- `mockups/package.json`은 `{"type":"commonjs"}` 한 줄이다. 저장소 루트 `package.json`이 `"type":"module"`이라 이 디렉터리의 `.js`를 Node가 CommonJS로 읽게 하며, 브라우저에는 영향이 없다.

### 6.2 합성 데이터

- 여행: "방콕 4박", 기준 통화 KRW, 여행 종료일 2026-08-30.
- 멤버 5명: 총무 현우, 참여자 민수·지은·서준·하린. 모두 가공 인물이며 별칭만 쓴다.
- 지출 12건: THB와 KRW가 섞여 있고 결제자·분담이 다양하며, 근거 상태는 원본 검수·OCR 미검수·수동 입력 세 종류를 데이터에 두고, 원본 삭제는 잠금 장면에서 원본 검수 상태로부터 파생되어 나타난다. 운영자 `case` 장면의 C-014에는 통화 미확정 1건과 미상 결제자 1건이 검수 차단 사유로 존재하고, 총무 검토 장면의 v2에는 제외 항목이 없다.
- 정산 버전 2개: v1은 지은의 이의로 수정되어 v2가 현재 버전이고, `participant_review` 장면에서는 v2에 서준의 이의 1건이 미해결 상태다.
- 케이스 3건: C-014(마감 대행형, 검수 중), C-013(검수형, 일시정지), C-012(검수형, 참여자 검토, 이의 1건).
- 환율: THB→KRW 두 시점 출처와 수동 사유 1건.

### 6.3 기술 제약

- 빌드 도구, 번들러, 프레임워크, 외부 JS 라이브러리를 쓰지 않는다.
- 서체는 Google Fonts(Fraunces, Space Mono)와 Pretendard CDN을 쓰고 Space Grotesk와 Inter는 불러오지 않는다.
- 외부 데이터 요청과 폼 전송은 없다. 폼 제출은 화면 안에서 결과만 바꾼다.
- 실제 개인정보, 계좌번호, 실제 영수증 이미지를 넣지 않는다. 영수증 자리는 회색 자리 표시로 대신한다.
- `public/`과 `vercel.json`에서 목업을 참조하지 않는다.

## 7. 검증과 수용 기준

### 7.1 시각 검증

- 브라우저 패널에서 375, 768, 1180px 세 폭으로 3.3의 모든 장면을 캡처한다.
- 각 캡처에서 가로 스크롤이 생기지 않고 서류 컴포넌트가 잘리지 않아야 한다.

### 7.2 접근성 체크리스트

- 본문 대비 AA 이상.
- 포커스 링이 모든 상호작용 요소에 보인다.
- 터치 대상 44px 이상.
- 헤딩 구조가 h1부터 순서대로 이어진다.
- 스탬프와 태그에 텍스트 대체가 있다.
- 모달이 포커스를 가두고 Esc로 닫힌다.

### 7.3 내용 규칙 체크리스트

- 모티프 예산 규칙 1~4와 6~7을 모든 화면이 지킨다.
- 표현색이 검토·공유·운영자 화면에 없고, 랜딩 특징 카드에서 같은 색이 연속되지 않는다.
- 한글 제목 굵기가 600을 넘지 않고 채운 버튼이 규칙 7의 수를 넘지 않는다.
- 모든 금액이 숫자 서체와 글자 라벨로 표시된다.
- 계좌번호, 은행명, Toss 링크, 영수증 원본이 어떤 화면에도 없다.
- 참여자 화면에 다른 참여자의 상세 지출이 없다.
- 법률 검토 전 문구에 "검토 전 문구" 표시가 있다.

- 3장의 케이스 상태, 4.2절의 가격 조건, 5.3절의 체크포인트, 11.3절의 불변식, 13장과 14.3절의 제한은 상위 명세의 승인된 설계 정책이며 이 문서는 이를 화면에 옮긴 것이다.
- 4장의 토큰 값, 컴포넌트 규칙, 모티프 예산과 5장의 배치는 이 문서의 설계 결정이다.
- 4.8절의 참고 디자인 분석 두 건은 사용자가 제공한 외부 문서이며, 각 항목의 채택·제외는 이 문서의 설계 결정이다.
- 6.2의 합성 데이터는 시연용 가정이며 실제 고객 사례가 아니다.
- 참여자 고지 문구, 약관, 개인정보 문구의 확정은 외부 전문 검토 결과에 따르며 이 문서의 자리 표시 문구는 그 결과를 대신하지 않는다.
