## 1. Codex 독립 감사

인증/DB 계약과 운영/개인정보/복구 계약을 서로 다른 읽기 전용 검토자에게 배정했다.

| 발견 사항 | 반영 내용 | 확인 결과 |
|---|---|---|
| 상위 Production 데모 허용과 최신 승인 충돌 | 항상 404, 직접 API·정적 파일 별칭 포함 | 해소 |
| 기존 리드 승격·보유 정책과 전량 demo 폐기 결정 충돌 | 격리·암호화 덤프 확인 후 폐기, 동의 소급 금지 | 해소 |
| Admin/Reviewer/Migration 외 시스템 작업 권한 공백 | auth, lead-ingest, privacy-job의 좁은 역할·함수 | 해소 |
| 부모 trip 분류만으로 자식 계좌·교차 여행 참조 미보호 | 자식·분류 변경·FK 부정 테스트 계약 | 해소 |
| Admin 원문 열람 감사 우회 | raw SELECT 차단, 감사와 원문 반환의 제한 함수 | 해소 |
| JWT/getUser만으로 폐기·절대수명 보장 불가 | 실제 session_id 행·user 일치, 최초 시각, 앱 폐기 선기록 | 해소 |
| CI가 0008까지만 검증 | 해당 시점 전체 마이그레이션, 00 완료 시 0009 포함 | 해소 |
| 리드 30일 anchor 불명확 | 최초 접수일+30일, 임의 연장 없음 | 해소 |
| tombstone 만료·삭제 중 장애 공백 | 외부 durable intent 선기록, pending 재적용·만료 금지, 마지막 관련 백업 만료+7일 | 해소 |
| 마이그레이션 후 원본 backup checksum 비교 오류 | 복원 직후 원본 검증→변환 후 검증→재삭제 검증으로 분리 | 해소 |
| 직원 UUID/HMAC을 익명정보로 오해 | 접근 제한된 가명 보안정보와 명시 보유기간 | 해소 |

두 검토자는 수정된 관련 절을 재확인했고 각 검토 범위 내 문서 blocker가 남지 않았다고 보고했다. 이는 보안 구현 또는 출시 검증 완료를 뜻하지 않는다.

## 2. Claude 독립 검토

- 실제 Claude Code CLI `2.1.107`로 두 명세의 읽기 전용 독립 검토를 요청했다.
- 사용 가능 도구를 Read로 제한하고 MCP·skills·hooks·Chrome 연동을 비활성화했다. 고객 데이터·비밀값은 제공하지 않았다.
- 첫 시도는 OAuth access token 만료로 HTTP 401이었다. 해당 시도는 API 입력·출력 토큰 0이며 실제 검토가 시작되지 않았다.
- 사용자가 재로그인을 완료한 후 동일 범위로 재시도했다. CLI 로그인 상태 정상 확인 후 실제 검토가 성공했다(exit 0, is_error=false).
- 검토 모델은 CLI 기본 설정의 `claude-opus-4-6[1m]`이었다. 모델을 임의 변경하지 않았다.
- 결과: 두 명세 전수 대조에서 구현을 차단하는 문서 blocker 없음. 다음 비차단 명확화 4건을 반영했다.

| 항목 | Claude 분류 | 반영 |
|---|---|---|
| `auth.sessions` 접근 경로 연결 | 중간·명확화 | NOLOGIN 소유 보안 정의자 함수, auth 역할에는 EXECUTE만 부여 명시 |
| QA 입력 제한을 UI에만 의존할 가능성 | 낮음·선택 개선 | 서버·DB의 길이 및 상태 코드 검증, 개인정보 완전 탐지로 과장하지 않음 |
| 고지 버전/정책 버전 용어 | 낮음·정합성 | 상위 `policy_version`으로 통일하고 의미 병기 |
| privacy-job 수정 금지와 삭제 허용의 혼동 | 낮음·명확화 | 임의 UPDATE 및 제한 함수 밖 DELETE 금지로 구분 |

Claude는 Production 차단, 플래그, 보유기간, tombstone 만료, 분류, 마이그레이션, 초기화 예외, 삭제 순서, CI, 비목표와 직원 역할의 상위·하위 정합성을 확인했다. 외부 공급자·개인정보 검토 입력은 이미 명시된 실행/출시 전제이며 문서 blocker가 아니라고 구분했다. 문구 보강 후 Codex가 변경 범위와 정합성을 확인했으며, 구현 보안이 검증된 것으로 해석하지 않는다.

## 3. 실행한 검증

| 검사 | 결과 |
|---|---|
| `git diff --check` | 통과 |
| 두 명세의 로컬 Markdown 링크 | 대상 파일 존재 확인 |
| `npm run typecheck` | 통과 |
| `npm test` | 49 passed, 0 failed |
| `npm run smoke:mcp` | 기본 도구 11개와 입력 schema 검증 통과 |
| `npm audit --omit=dev --json` | 실패(exit 1), High 5·Moderate 2·Critical 0 |

audit 집계는 영향 패키지 기준이다. High: `fast-uri`, `image-size`, `ip-address`, `nanoid`, `pptxgenjs`. Moderate: `@hono/node-server`, `hono`. 이는 알려진 취약 의존성이 있다는 증거이며 각 경로의 실제 악용 가능성을 확정한 결과는 아니다. 해결·영향 검토·승인된 한시적 예외 여부는 00A 구현에서 다룬다. 문서 작업을 이유로 패키지 버전을 변경하거나 audit를 통과한 것으로 표시하지 않았다.

## 4. 남은 순서

1. 작성된 하위 명세에 대한 사용자 최종 승인
2. `writing-plans` 구현 계획 작성
3. 구현 계획의 별도 실행 승인

외부 보관소·실제 요금제/리전·직원 등록값·개인정보 전문 검토는 명세에 명시된 실행/출시 전제다. 문서 승인으로 이 전제를 충족하거나 신규 서비스를 구매한 것으로 간주하지 않는다.
